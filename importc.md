ImportC — это компилятор C, встроенный в реализацию D. Он позволяет напрямую импортировать файлы C, без необходимости вручную подготавливать файл D, соответствующий объявлениям в файле C. Он напрямую компилирует файлы C в модули, которые могут быть связаны с кодом D для формирования исполняемого файла. Его можно использовать как компилятор C для компиляции и компоновки программ, полностью написанных на C.

Примечание: ImportC и BetterC — это совершенно разные вещи. ImportC — это настоящий компилятор C. BetterC — это подмножество D, которое полагается только на существование стандартной библиотеки C. Код BetterC также может быть связан с кодом ImportC.
Краткие примеры
Код на языке C в файле hello.c :

#include <stdio.h>
int main()
{
    printf("hello world\n");
    return 0;
}
Скомпилируйте и запустите:

dmd hello.c
./hello
hello world
Функция на языке C в файле functions.c :

int square(int i)
{
    return i * i;
}
Программа на языке D в файле demo.d :

import std.stdio;
import functions;
void main()
{
    int i = 7;
    writefln("The square of %s is %s", i, square(i));
}
Скомпилируйте и запустите:

dmd demo.d functions.c
./demo
The square of 7 is 49
ImportC Диалект
Существует множество версий языка C. ImportC является реализацией стандарта ISO/IEC 9899:2011 , который будет обозначаться как C11 . Ссылки на стандарт C11 будут обозначаться как C11 с последующим номером параграфа. Более ранние версии, такие как C99, C89 и K+RC, не поддерживаются.

Определение реализации: Диалект ImportC корректируется в соответствии с поведением компилятора C, с которым связан компилятор D, т.е. ассоциированного компилятора C.
Вносятся дополнительные корректировки для использования некоторых возможностей реализации D.

Примечание: Это не справочник по языку C и не учебное пособие по программированию. В нем описываются особенности диалекта языка C, к которому относится ImportC, и способы его эффективного использования.

Препроцессор
ImportC не имеет препроцессора. Он предназначен для компиляции файлов C после их предварительной обработки препроцессором C. ImportC может автоматически запускать препроцессор C, связанный с соответствующим компилятором C , или же препроцессор можно запустить вручную.

Автоматический запуск препроцессора
Если файл C имеет расширение .c , ImportC автоматически запустит для него препроцессор.

При компиляции для Windows с ключом -m32omf в качестве препроцессора будет использоваться sppn.exe .
При компиляции для Windows с ключом -m32mscoff или -m64 в качестве препроцессора будет использоваться cl.exe /P /Zc:preprocessor .
При компиляции для OSX будет использоваться препроцессор clang -E .
В противном случае будет использоваться препроцессор C++ .
Ключ -v можно использовать для отслеживания команды, которая вызывает препроцессор.

Ключ -P preprocessorflag передает параметр preprocessorflag препроцессору.

импортc.h
Файл druntime src/importc.h будет автоматически включен первым с помощью директивы #include d. Файл importc.h содержит изменения в исходном коде, учитывающие различные расширения компилятора C, не поддерживаемые ImportC.

no-builtin-macro-redefined
В системах Posix ImportC передаёт параметр -Wno-builtin-macro-redefined препроцессору C, используемому gcc и clang . Этот параметр отсутствует в препроцессорах gcc, выпущенных до 2008 года. В качестве обходного пути можно запустить препроцессор вручную.

Запуск препроцессора вручную
Если файл на языке C имеет расширение .i , считается, что он уже прошел предварительную обработку. Предварительную обработку можно запустить вручную:

Digital Mars C Preprocessor sppn.exe
sppn.exe работает на Win32 и запускается следующим образом:

sppn file.c
и предварительно обработанные выходные данные записываются в файл file.i.

Препроцессор Gnu C
Препроцессор Gnu C можно вызвать следующим образом:

gcc -E file.c > file.i
Препроцессор Clang C
Препроцессор Clang можно вызвать следующим образом:

clang -E file.c -o file.i
Препроцессор Microsoft VC
Препроцессор VC можно вызвать следующим образом:

cl /P /Zc:preprocessor file.c -Fifile.i
и предварительно обработанные выходные данные записываются в файл file.i.

Препроцессор dmpp C
Препроцессор dmpp на языке C можно вызвать следующим образом:

dmpp file.c
и предварительно обработанные выходные данные записываются в файл file.i.

Макросы препроцессора
ImportC автоматически собирает все макросы #define, созданные препроцессором во время его автоматического запуска. Некоторые из них могут быть доступны для кода на языке D, если интерпретировать их как объявления. Разнообразие макросов, которые могут быть интерпретированы как объявления на языке D, может быть расширено, но никогда не охватит все возможности метапрограммирования с использованием макросов на языке C.

Явные константы
Макросы, которые выглядят как явные константы, например:

#define COLOR 0x123456
#define HELLO "hello"
интерпретируются как постоянные заявления D в форме:

enum COLOR = 0x123456;
enum HELLO = "hello";
Макросы, похожие на функции
Многие макросы выглядят как функции и могут рассматриваться как шаблонные функции:

#define ABC a + b
#define DEF(a) (a + x)
auto ABC() { return a + b; }
auto DEF(T)(T a) { return a + x; }
Однако некоторые макроформулы не дадут того же результата:

#define ADD(a, b) a + b
int x = ADD(1, 2) * 4; // sets x to 9
auto ADD(U, V)(U a, V b) { return a + b; }
int x = ADD(1, 2) * 4; // sets x to 12
Рекомендации: Всегда заключайте аргументы и целые выражения в скобки:
#define ADD(a, b) ((a) + (b))
Ещё одна проблемная область — побочные эффекты в аргументах:

#define DOUBLE(x) ((x) + (x))
int i = 0;
DOUBLE(i++);
assert(i == 2);  // D result will be 1, C result will be 2
и рассматривая аргументы как ссылки:

#define INC(x) (++x)
int i = 0;
INC(i);
assert(i == 1); // D result will be 0, C result will be 1
Предопределенные макросы
Функция ImportC не определяет никаких макросов заранее.

Чтобы отличить компиляцию, выполненную с помощью ImportC, от компиляции с помощью другого компилятора C, используйте:

#if __IMPORTC__
Функция __IMPORTC__ определена в файле src/importc.h , который автоматически включается при запуске препроцессора. Файл importc.h содержит множество определений макросов, используемых для адаптации различных особенностей исходного кода C к функции ImportC.

Перечисления
Константы перечисления всегда имеют тип целых чисел.

Существует множество аспектов битовых полей C11, определяемых реализацией. Поведение ImportC подстраивается под поведение соответствующего компилятора C на целевой платформе.

Неявные объявления функций:

Несоответствие импедансов
Несмотря на все усилия по согласованию языков C и D таким образом, чтобы они "просто работали", между ними существуют некоторые фундаментальные различия, которые время от времени проявляются.

Несоответствие ключевых слов
В языках D и C используются в основном одни и те же ключевые слова, в C есть ключевые слова, которых нет в D, и наоборот. Это не влияет на компиляцию кода на C, но может вызвать трудности при доступе к переменным и типам C из D. Например, в DversionВ языке C ключевое слово `keyword` нередко используется в качестве члена структуры:

Код на языке C в файле defs.c :

struct S { int version; };
Доступ к нему с диска D:

import defs;
int tech(S* s) {
    return s.version; // fails because version is a D keyword
}
Существует обходное решение:

import defs;
int tech(S* s) {
    return __traits(getMember, *s, "version");
}
Одинаковые, только разные типы.
На некоторых платформах Clongиunsigned longимеют тот же размер, что иintиunsigned intсоответственно. На других платформах Clongиunsigned longимеют тот же размер, что иlong longиunsigned long long. long doubleиlong double _Complexможет быть того же размера, что иdoubleиdouble _ComplexВ ImportC типы, имеющие одинаковый размер и знаковую структуру, рассматриваются как один и тот же тип.

_Generic
Обобщенные выражения выбора (C11 6.5.1.1) отличаются от ImportC. Типы в Same only Different Types неразличимы в частях имен типов в generic-association . Вместо того чтобы выдавать ошибку для повторяющихся типов согласно C11 6.5.1.1-2, ImportC выберет первое совместимое имя типа в списке generic-assoc-list .

Ссылки на последующие публикации
Доступ можно получить к любым объявлениям в области видимости, а не только к объявлениям, которые лексически предшествуют ссылке.

Ta *p;  // Ta is forward referenced
struct Sa { int x; };
typedef struct Sa Ta; // Ta is defined
struct S s;
int* p = &s.t.x;  // struct S definition is forward referenced
struct S { int a; struct T t; }; // T still forward referenced
struct T { int b; int x; }; // definition of struct T
Символы тегов стиля C++
В C++,struct,unionилиenumДоступ к символам тегов возможен без необходимости добавления префикса.struct,unionилиenumключевые слова, если нет другого объявления с тем же именем в той же области видимости. ImportC ведет себя аналогично.

Например, следующий код принимается как C++, так и ImportC:

struct s { int a; };

void g(int s)
{
    struct s* p = (struct s*)malloc(sizeof(struct s)); // unambiguous
    p->a = s;
}
Однако этот код отклоняется как в C++, так и в ImportC по той же причине.

struct s { int a; };

void g(int s)
{
    s* p = (s*)malloc(sizeof(s)); // error: parser matches s to int s
    p->a = s;
}
Выполнение функций во время компиляции
Вычисление константных выражений включает в себя выполнение функций таким же образом, как это делает CTFE в языке D. Константное выражение вызывает вычисление во время компиляции.

Примеры:

_Static_assert("\x1"[0] == 1, "indexing should be 1");

int mint1() { return -1; }
_Static_assert(mint1() == -1, "call should be -1");

const int a = 7;
int b = a; // sets b to 7

Функция импорта также позволяет коду ImportC напрямую импортировать другие файлы C без необходимости создания файла..hТакже, для них создается соответствующий файл. Импортированные функции C становятся доступными для встраивания.

Функция ImportList работает так же, как и для D.

Порядок расположения объявлений CImportDeclaration не имеет значения.

Файл ImportC можно импортировать, при этом имя импортируемого файла C определяется именем модуля.

Все глобальные символы в файле ImportC становятся доступными для модуля импорта.

Если имя, указанное в импортируемом файле, не найдено, выполняется поиск этого имени среди глобальных символов в каждом импортируемом файле. Если оно найдено ровно в одном модуле, это и становится разрешением имени. Если оно найдено в нескольких модулях, это ошибка.

Примечание: Поскольку в ImportC отсутствует оператор разрешения области видимости, можно найти только глобальные символы, и нельзя добавить указание на то, в каком модуле находится символ.

Символы тегов
Символы тегов — это идентификаторы, которые появляются послеstruct,union, иenum ключевые слова (C11 6.7.2.3). В языке C они помещаются в отдельную таблицу символов, отличную от других идентификаторов. Это означает, что два разных символа могут использовать одно и то же имя:

int S;
struct S { int a, b; };
S = 3;
struct S *ps;
В языке D такого различия не делается. Если в качестве идентификатора указан только один тег, компилятор D распознает именно его. Если же есть тег и не-тег, имеющие общий идентификатор, компилятор D распознает не-тег. Обычно это не является проблемой благодаря распространенной в языке C практике примененияtypedefкак в:

typedef struct S { int a, b; } S;
Компилятор D распознаетtypedefприменяется кSИ код компилируется как ожидалось. Но когдаtypedefотсутствует, например:

int S;
struct S { int a, b; };
Наиболее прагматичным обходным путем является добавлениеtypedefк коду на языке C:

int S;
struct S { int a, b; };
typedef struct S S_t;    // add this typedef
Затем компилятор D может получить доступ к символу тега структуры черезS_t.

Преобразование кода на языке C в код на языке D
Иногда желательно пойти дальше импорта кода на языке C и выполнить преобразование исходного кода с C в исходный код на языке D. Причины этого следующие:

Перенос проекта, написанного на языке C, в проект, написанный на языке D.
Эквивалентный код на языке D компилируется гораздо быстрее, поскольку не требует препроцессора и т.д.
Доработка кода на языке D для добавления атрибутов, обеспечивающих безопасность памяти, чистоту и т.д.
Устранение необходимости использования синонимов в части проекта, относящейся к категории D.
Это можно сделать с помощью компилятора D, используя ключ -Hf :

dmd -c mycode.c -Hf=mycode.di
Эта команда преобразует исходный код на языке C из файла mycode.c в исходный код на языке D из файла mycode.di . Если также используется ключ -inline , она будет генерировать и тела функций на языке C, а не только прототипы функций.

Несоответствие импедансов
Точное сопоставление семантики C со всеми её особенностями с исходным кодом D не всегда осуществимо. ImportC использует семантику C в своём семантическом анализе, чтобы приблизиться к точной семантике C гораздо ближе, чем это возможно выразить в исходном коде D. Следовательно, перевод в исходный код D будет далёк от совершенства. Например:

int S;
struct S { int a, b; };
int foo(struct S s)
{
    return S + s.a;
}
В ImportC всё будет работать нормально, потому чтоint Sиstruct SОни находятся в разных таблицах символов. Но в сгенерированном коде на языке D оба символа будут находиться в одной таблице символов и будут конфликтовать. Такой исходный код на языке D, переведенный с языка C, потребует корректировки со стороны пользователя.

Тем не менее, по отзывам с мест, эта возможность преобразования значительно экономит время пользователей, которым приходится работать с существующим кодом на языке C.

Предупреждения:
Многие подозрительные конструкции в языке C обычно по умолчанию вызывают предупреждения со стороны стандартных компиляторов, например:
int *p = 3; // Warning: integer implicitly converted to pointer

ImportC не выдает предупреждений. Предполагается, что пользователь будет импортировать существующий код на языке C, разработанный с использованием другого компилятора C, и что он написан так, как задумано. Если C11 подтверждает его допустимость, ImportC принимает его.
