# selNtc.md — Отчёт СДАНК по удостоверениям (тип сертификата 2): схема, связи, правила

Документация для AI-агентов. Итог исследования БД **MS SQL db-docs** (DSN `db-docs`,
QODBC, read-only) для построения отчёта по сертификатам/удостоверениям с
`Код_Типа_сертификата = 2` («Удостоверение (ПБ 03-440-02 Ростехнадзора)»).

Рабочие файлы: `apps/reestr/report_sdank_type2.sql` (отчётный запрос),
`apps/reestr/explore.exe` (read-only прогон SQL, см. ниже), эталон формата —
`apps/reestr/1k_10.txt` (2462 строки × 22 поля, разделитель `|`; старый снимок,
только как пример структуры — данные в нём могут отсутствовать в текущей БД).

---

## 1. Главное: якорь отчёта — таблица Обращения, а НЕ Сертификаты

- В `Сертификаты` записи типа 2 с заполненной `[Дата выдачи]` заканчиваются
  **18.02.2011** (таких всего 20). Остальные **13196** записей типа 2 имеют
  `[Дата выдачи] = NULL` — это актуальный реестр, из него берётся **только номер**.
- Живые данные типа 2 — в `Обращения` (`Код_Типа_серт_уд = 2`,
  `Срок_действия_удостоверения IS NOT NULL`): непрерывно с 2000 по 2031 гг.
  (2026 → 1444 обращения по дате обращения; 1267 уникальных за 2026 при фильтре
  по сроку действия).
- Связи `Сертификаты → Обращения` нет вообще: джойн только по
  `(Код учащегося, Код_типа_сертификата)`, что у одного человека даёт 1–2 записи
  (`0018-22758` и `0018-10-22758` одновременно). Правило: `MAX(№сертификата)`
  через `OUTER APPLY` — дубли схлопываются, 1 строка = 1 обращение.
- У части обращений записи в `Сертификаты` нет → номер пустой (это норма).

## 2. Карта полей отчёта

| Поле | Источник | Примечание |
|---|---|---|
| Номер_Сертификата | `Сертификаты.[№сертификата]` | MAX по учащемуся+типу (OUTER APPLY) |
| Фамилия, Имя, Отчество, Дата_Рождения | `Спр_учащихся` | дата рождения → `CONVERT(...,104)` |
| Должность | `Список учащихся по организациям.Должность` | через `Обращения.Код_учащегося_в_орг` |
| Система | константа `СДАНК-02-2020` | литерал в SELECT; во всём эталоне одинакова |
| Метод | `Спр_методы_контроля.Метод` | краткий код (МК/VT/PT…), НЕ МетодРУС |
| Тип | `Спр_Виды_аттестаций.вид_аттестации` | «первичная/повторная/продление» — это вид аттестации, не тип сертификата! |
| Объекты | `Обращения.Список_объектов` | |
| Дата_Начала | вычисляемая, см. §3 | |
| Дата_Окончания | `Обращения.Срок_действия_удостоверения` | |
| ИНН | `спр_организаций.ИНН` (decimal) | если NULL — парсинг цифр после «ИНН» из `спр_организаций.[Доп сведения]` |
| Наименование_Организации | `спр_организаций.Название` | |
| Адрес_Юридический | `спр_организаций.[Юридический адрес]` | |
| Адрес_Почтовый | `спр_организаций.Адрес` | |
| e_mail | `спр_организаций.[E-mail]` | |
| КодПодразделения | парсинг из №сертификата | префикс до первого `-`, добитый нулями до 4: `18-06808-00` → `0018`, `0018-6856` → `0018` |
| Регион («?» спецификации) | `спр_организаций.[Код региона]` | |
| d1, d2 | `Обращения.d1`, `Обращения.d2` | выводить КАК ЕСТЬ; датами действия НЕ являются (заполнены редко: d1 — 4, d2 — 65 из 1361 за 2026) |
| НомерГолограммы | `Обращения.hologram` (int) | колонка добавлена в БД 2026-09; в `Направления` d1/d2/hologram отсутствуют |

Цепочка джойнов (проверена, повторяет mgw_query.sql / AttSdank.sql):

```
Обращения о
  INNER JOIN Спр_учащихся у            ON о.Код_учащегося        = у.[Код учащегося]
  INNER JOIN Спр_методы_контроля м     ON о.Код_метода           = м.[Код метода]
  INNER JOIN Спр_Виды_аттестаций ва    ON о.Код_вида_аттестации  = ва.код_вида_аттестации
  INNER JOIN Список учащихся по организациям лу
                                     ON о.Код_учащегося_в_орг  = лу.[Код учащегося по орг]
  INNER JOIN спр_организаций орг     ON лу.[Код организации]    = орг.Код_орг
  OUTER APPLY (SELECT MAX(с.[№сертификата]) FROM Сертификаты с
               WHERE с.[Код учащегося] = о.Код_учащегося
                 AND с.Код_типа_сертификата = о.Код_Типа_серт_уд) серт
```

Один человек с несколькими методами = несколько обращений = несколько строк
отчёта (как в эталоне). Организация одна на обращение (через
`Код_учащегося_в_орг`) — дублей по оргам нет.

## 3. Правила по датам (решения владельца отчёта)

1. **Период отчёта задаётся двумя датами-литералами в WHERE**; первая дата
   **входит**, последняя **не входит**: `>= 'YYYYMMDD' AND < 'YYYYMMDD'`.
   Guard explore.exe не пропускает `DECLARE` — только литералы.
2. **Дата_Окончания** = `Обращения.Срок_действия_удостоверения`.
3. **Дата_Начала** = Дата_Окончания **строго минус срок действия по уровню**:
   `Код_уровня` 1 или 2 → **−3 года**, `Код_уровня` 3 → **−5 лет**
   (`DATEADD(YEAR, -3|-5, о.Срок_действия_удостоверения)`).
   Совпадает со справочником `Спр_Типы_сертификатов` (тип 2: 1-2 ур. — 3 года,
   3 ур. — 5 лет) и с эталоном (25.03.2022 → 25.03.2025).
4. Почему не хранимые поля: `Обращения.[дата выдачи]` пусто у **всех** записей
   типа 2 (0 из 1267 за 2026); `d1/d2` заполнены у единиц и используются только
   как информационные колонки.
5. Даты в выводе — `CONVERT(VARCHAR(10), дата, 104)` → `dd.mm.yyyy`.

## 4. Особенности данных, найденные разведкой

- `Спр_Типы_сертификатов`: 1 = ISO 9712, **2 = Удостоверение ПБ 03-440-02**,
  4 = Удостоверение Ростехнадзора, 7 = Сертификат ТН, 8 = Разрешение АК Транснефть.
  После 2015 г. в `Сертификаты` пишутся только типы 1, 7, 8.
- Номера типа 2 имеют префикс подразделения: `0018-…`, `18-…` (старого формата),
  вариант с инфиксом `0018-10-22758`.
- ИНН организации — `decimal` (ведущие нули теряются), бывает NULL; запасной
  источник — текст `[Доп сведения]` (встречается «ИНН …»).
- Адреса организаций — `ntext`; в эталоне юр. и почтовый адреса часто совпадают.
- На сервере есть другие БД (db-AS, db-rk, db-std…), но учётке `stepina` доступна
  **только db-docs** — кросс-базовые запросы запрещены сервером.
- `sys.databases`, `INFORMATION_SCHEMA` — читаются; `sys.*` частично.

### Направления → Обращения (фильтр по строке направления)

- Пользователь выбирает строку в `Направления` (по `№направления`, напр.
  `'213/2026'` → `Код_направления = 22535`), она фильтрует `Обращения`.
- Код направления в `Обращения` живёт в **двух** колонках — два потока:
  `Код_направления_УЦ` и `Код_направления_ЭЦ`. Надёжный join — через
  `IN (о.Код_направления_УЦ, о.Код_направления_ЭЦ)`.
- Для '213/2026' совпадения только по ЭЦ: 17 строк (все метод UT, август 2026,
  тип сертификата смешанный 1/2). По УЦ — 0.
- Готовый запрос: `obr_po_napravleniyu.sql` (номер направления — литерал
  в WHERE).

## 5. Инструмент запуска: explore.exe (read-only)

`apps/reestr/explore.exe` (исходник `explore.d`) — консольный прогон SELECT'ов
против db-docs; guard отклоняет всё, кроме одиночного SELECT/WITH (exit 3).

```
explore.exe report_sdank_type2.sql --csv=sdank2.csv --limit=20
explore.exe --tables | --columns <таблица> | --top <таблица> [N]
```

Вывод: консоль (`;`, dd.mm.yyyy) + опциональный CSV с заголовком колонок.
Конфиг подключения — `[DB]` в `apps/reestr/reestr.ini`.

## 6. Статус report_sdank_type2.sql

- Реализованы: все поля §2, правило 1 (период литералами), правило 2,
  парсинг ИНН и КодПодразделения, OUTER APPLY-дедуп номеров.
- Правило 3 (Дата_Начала = Окончание − 3/5 лет по `Код_уровня`) — **отложено**
  по указанию владельца; сейчас Дата_Начала = `Дата_обращения`
  (временная подстановка). Перед внедрением уточнить, по какому полю фильтровать
  период: `Дата_обращения` или `Срок_действия_удостоверения`.
- Прогон за 2026 (период по Дата_обращения, `[2026-01-01, 2027-01-01)`):
  **1267 строк** = числу уникальных обращений — дублей нет.
