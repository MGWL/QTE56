# Callback'и в forthD: вызов Форт-слова из внешнего кода

Механизм создания **точек входа в Форт** для внешнего мира: Windows
(WndProc, EnumWindowsProc, таймеры), C-библиотеки (компаратор qsort),
любая DLL, которая вызывает переданный ей адрес функции.

Поддерживаются два соглашения о вызовах: **stdcall (WINAPI)** и **cdecl**.
Различие между ними - только в том, кто снимает аргументы с машинного
стека (см. раздел "Соглашения вызовов").

Обратное направление (Форт вызывает DLL) описано в `call.md` / stdlib.f
(`_-Call"`, `WINAPI-Call"`, `CDECL-Call"`). Оба направления стыкуются:
из callback'а можно вызывать DLL обычными словами вызова (см. "Вложенные
вызовы").

---

## 1. Быстрый старт

```forth
\ 1. Написать обычное Форт-слово с контрактом ( a1..aN -- res )
: ON-COMPARE ( a b -- res ) 2DUP = IF 2DROP 0 ELSE < IF -1 ELSE 1 THEN THEN ;

\ 2. Изготовить thunk (точку входа) - в ИНТЕРПРЕТАЦИИ (см. п. 8.3 про ')
' ON-COMPARE 2 MK-CDECL-CB CONST CMP-CB

\ 3. Передать CMP-CB внешнему миру как адрес функции
\    (например, аргументом qsort или полем lpfnWndProc структуры WNDCLASSEX)
```

Два слова-фабрики (stdlib.f):

| Слово | Соглашение | Стек чистит |
|---|---|---|
| `MK-WINAPI-CB ( xt n -- addr )` | stdcall / WINAPI | callback (`ret 4*N`) |
| `MK-CDECL-CB ( xt n -- addr )` | cdecl | вызывающий (`ret`) |

Оба возвращают **addr** - адрес thunk'а в кодофайле. Именно он отдаётся
наружу как указатель на функцию. `xt` - CFA слова (через `'`), `n` -
число аргументов внешнего прототипа (0..63, см. п. 7).

Третье слово - `CBRIDGE ( -- addr )` - выдаёт адрес моста cbBridge;
нужно только самим фабрикам, пользователю не требуется.

---

## 2. Контракт callback-слова

Слово обязано иметь стек-эффект **( a1..aN -- res )** и быть
сбалансированным по всем стекам:

- **Стек данных**: снять ровно N ячеек, оставить ровно одну (результат).
  Недобор/перебор мост не проверяет - контекст ФВМ испортится молча.
- **Стек возвратов** (ESP, он же native-стек): на нём лежит адрес
  возврата моста. `>R` без парного `R>` внутри слова разрушит возврат.
- **L-стек (ESI) и R2-стек (EDI)**: пользоваться можно, но к выходу
  указатели должны вернуться к входным значениям (парные `>L`/`L>`,
  `L{ ... }L` и т.п.).

**Порядок аргументов**: первый аргумент внешнего прототипа лежит ГЛУБЖЕ
всех, последний - на вершине (TOS). Пример: WndProc Windows
`LRESULT WndProc(HWND hwnd, UINT msg, WPARAM w, LPARAM l)` превращается в

```forth
: WPH ( hwnd msg wparam lparam -- res ) ... ;
```

**Результат**: 32-битная ячейка, возвращается вызывающему в EAX
(стандарт для обоих соглашений). Типовое для WndProc - вернуть 0/1 или
результат DefWindowProc.

**THROW внутри callback'а НЕ перехватывается** (осознанное решение
проекта): чекпойнт размотки стоит на границе D<->Форт, а поверх неё в
native-стеке лежат чужие кадры - размотка туда бессмысленна. Считайте,
что THROW в callback'е роняет процесс. Отлаживайте слово заранее в REPL
(п. 8.1).

## 3. Соглашения вызовов

### 3.1. Общее

Оба соглашения (32 бита):
- аргументы кладутся на стек **справа налево** (первый аргумент
  прототипа оказывается по младшему адресу);
- результат возвращается в **EAX**;
- регистры EBX, ESI, EDI, EBP - callee-saved (callback обязан их
  сохранить - это делает мост, см. п. 5.2);
- регистры EAX, ECX, EDX - volatile.

### 3.2. Различие: кто чистит стек

| | stdcall (WINAPI) | cdecl |
|---|---|---|
| Снимает аргументы | **callback** (`ret 4*N`) | **вызывающий** (`add esp,4*N` после `call`) |
| Завершение thunk'а | `C2 lo 00` (`ret imm16`) | `C3` (`ret`) |
| Фабрика | `MK-WINAPI-CB` | `MK-CDECL-CB` |
| Типичные случаи | WinAPI: WndProc, EnumWindowsProc, EnumFontProc, TimerProc, DLGPROC | C-библиотеки: компаратор qsort/bsearch, atexit, колбэки собственных DLL |

**Перепутать соглашение нельзя**: если stdcall-вызывающий позовёт
cdecl-thunk (или наоборот), ESP после возврата съедет на `4*N` байт -
дальше вызывающий испортится. Симптом: падение или мусор вскоре после
возврата из внешней функции, причём сам callback отработал правильно.

### 3.3. Как определить соглашение чужого прототипа

- Вся WinAPI - stdcall (`WINAPI`, `CALLBACK`, `PASCAL` в заголовках -
  это всё stdcall в Win32).
- C-библиотеки и код по умолчанию - cdecl (`extern(C)` в D, ничего не
  указано в C).
- Если есть .h/.def/документация - смотреть туда. Если сомнения -
  проверить баланс ESP вокруг вызова в тестовой DLL (см. п. 8.2,
  функция `cbw2_chk` делает именно это).

## 4. Что генерирует фабрика (thunk)

Thunk - крошечная машинная процедура в кодофайле (область HERE...,
выделена VirtualAlloc с PAGE_EXECUTE_READWRITE, поэтому исполняема).
Фабрики (stdlib.f):

```forth
: (MKCB)  ( xt n -- addr n )
    HERE -ROT
    $BA B, SWAP ,                  // mov EDX, xt
    $B9 B, DUP ,                   // mov ECX, n
    $E8 B, CBRIDGE HERE 4 + - , ;  // call cbBridge (rel32)
: MK-WINAPI-CB ( xt n -- addr )
    (MKCB) $C2 B, 4 * DUP B, DROP 0 B, ;   // ret 4*n
: MK-CDECL-CB ( xt n -- addr )
    (MKCB) DROP $C3 B, ;                   // ret
```

Для `' WORD 2 MK-WINAPI-CB` получаются байты:

```
BA <xt:4>        mov EDX, xt        ; CFA слова
B9 02 00 00 00   mov ECX, 2         ; N - число аргументов
E8 <rel:4>       call cbBridge      ; относительный вызов моста
C2 08 00         ret 8              ; stdcall: снять 4*N байт
```

Для cdecl-пары в конце вместо `C2 08 00` стоит один байт `C3` (`ret`).

Thunk не содержит адресов, зависящих от положения (кроме rel32 до моста,
вычисленного при генерации), и не меняется после изготовления - его адрес
можно отдавать наружу многократно.

## 5. Как это устроено внутри

### 5.1. Регистровая модель ФВМ (напоминание)

| Регистр | Назначение |
|---|---|
| EAX | TOS (вершина стека данных) |
| EBP | указатель стека данных (растёт вниз) |
| ESP | стек возвратов = native-стек |
| ESI | L-стек (локальные) |
| EDI | R2-стек |
| EBX | свободен / рабочий |

### 5.2. Мост cbBridge (forth.d)

Вход (от thunk'а): `EDX = xt`, `ECX = N`, на native-стеке:

```
[ESP]    адрес возврата в thunk
[ESP+4]  адрес возврата во внешний код (Windows/DLL)
[ESP+8]  arg1
[ESP+12] arg2
...      ...
[ESP+4+4N] argN
```

Шаги моста:

1. `push EBX/ESI/EDI/EBP` - сохранить регистры ВНЕШНЕГО кода (по ABI они
   callee-saved, мост обязан их вернуть). После этого arg1 = `[ESP+24]`.
2. `EBP/ESI/EDI <- gCbSaveEBP/gCbSaveESI/gCbSaveEDI` - контекст ФВМ
   берётся из СНИМКА (п. 5.3), а не из входных регистров.
3. `and ESP,-16` + сохранение старого ESP - выравнивание под movaps
   (код CRT/user32 падает на невыравненном SSE-доступе).
4. Раскладка аргументов на стек данных Форта (N>0): don't-care ячейка
   TOS-приёмника, затем arg1..arg(N-1) в память (EBP уходит вниз),
   argN -> EAX (TOS). Для N=3 (S = EBP из снимка):

   ```
   EAX    = arg3            (TOS)
   [S-12] = arg2            ([EBP] после раскладки)
   [S-8]  = arg1
   [S-4]  = TOS-приёмник    (прежняя вершина стека данных)
   ```

   При N=0 стек данных не трогается вовсе: h_DUP в начале самого слова
   компенсирует выходной DROP моста.
5. `call EDX` - выполняется Форт-слово `( a1..aN -- res )`.
6. Результат перекладывается в ECX (EBX занять нельзя - его восстановит
   pop), затем DROP результата со стека данных: `EAX <- [EBP]`,
   `EBP += 4`. После этого EBP равен значению из снимка - стек данных
   сбалансирован независимо от N.
7. Снятие выравнивания (`mov ESP,[ESP]`), `pop EBP/EDI/ESI/EBX` -
   регистры внешнего кода возвращены, `EAX <- ECX` (результат), `ret` -
   в thunk, далее `ret 4*N` / `ret` - во внешний код.

### 5.3. Снимок контекста gCbSave* - почему нельзя доверять входным регистрам

Искушение: считать, что в момент callback'а EBP/ESI/EDI всё ещё держат
контекст ФВМ, потому что "callee-saved регистры сохраняются по ABI".
Это неверно. ABI гарантирует, что внешняя функция вернёт эти регистры
**к моменту своего return** в Форт - но МЕЖДУ своим входом и вызовом
thunk'а она вольна держать в них что угодно: кадр (`enter/leave` кладёт
в EBP указатель на свой фрейм), счётчики и указатели (ESI/EDI/EBX -
типичные рабочие регистры оптимизатора). Если бы мост писал ячейки
"стека данных" относительно такого EBP, он затирал бы аргументы и
локальные переменные внешней функции.

Поэтому контекст снимается заранее: **callD (CALL_A) и callD2 (CALLB) -
оба шлюза Форт->внешний мир - перед каждым внешним `call ECX` пишут
живые EBP/ESI/EDI в глобалы `gCbSaveEBP/gCbSaveESI/gCbSaveEDI`**. Мост
читает контекст оттуда.

Следствия:

- **Callback легален только пока Форт приостановлен внутри внешнего
  вызова** (DispatchMessage, SendMessage, qsort, функция тестовой DLL и
  т.п.) - тогда снимок свежий. Thunk, позванный "мимо" внешнего вызова
  (из чужого потока, из D-кода, где Форт не на стеке), получит
  протухший снимок - поведение не определено.
- Снимок один (не стек) - достаточно, потому что актуален всегда
  снимок САМОГО ВНУТРЕННЕГО активного внешнего вызова (см. п. 6).

### 5.4. Что мост НЕ делает

- Не проверяет N и баланс слова (проверять - тестам, п. 8.2).
- Не перехватывает THROW (п. 2).
- Не пишет контекст обратно в gCbSave*: по контракту слово
  сбалансировано, EBP/ESI/EDI после него равны загруженным.

## 6. Вложенные вызовы и реентерабельность

Из callback'а можно вызывать DLL обычными словами вызова (`Call"`,
CALL_A, CALLB). Цепочка:

```
Форт -> Call" -> callD [снимок S1] -> DLL-1 -> thunk-1 -> cbBridge (S1)
  -> слово-1 -> Call" -> callD [снимок S2] -> DLL-2 -> thunk-2 -> cbBridge (S2)
    -> слово-2 -> ... -> ret -> DLL-2 -> ret -> callD -> слово-1 -> ...
```

Каждый вложенный внешний вызов перезаписывает снимок своим (внутренним)
контекстом - вложенный мост берёт именно его. После возврата из
внешнего вызова работа продолжается на ЖИВЫХ регистрах (внешний код
вернул callee-saved по ABI), поэтому обратной выгрузки снимка не нужно.
Проверено тестом CBNEST (test/cb_test.f): callback, изнутри вызывающий
DLL, которая снова вызывает callback.

Этим же снят исторический запрет "из реального колбэка нельзя звать
DLL": он происходил из старого механизма (wndProcBridge + GSAVE), где
контекст снимался вручную и не всегда вовремя.

## 7. Ограничения

- **N <= 63** для `MK-WINAPI-CB`: фабрика пишет `4*N` младшим байтом
  `ret imm16` (старший - 0). Реальные прототипы укладываются с запасом
  (WndProc: 4, CreateWindowExA - не callback). Для `MK-CDECL-CB`
  ограничения нет (в конце просто `ret`).
- **Ячейка 32 бита**: аргументы и результат - по одной ячейке.
  64-битные значения (LARGE_INTEGER и т.п.) по значению не передаются -
  только через указатели.
- **Однопоточность**: одна ФВМ, один комплект gCbSave*. Callback из
  другого потока ОС не поддерживается.
- **Время жизни thunk'а** = время жизни кодофайла (процесса). Не
  отдавать адрес наружу дольше, чем жив процесс. Слово по xt должно
  существовать всё время, пока thunk могут позвать.
- **xt только через `'` в интерпретации** (п. 8.3).

## 8. Отладка callback'ов

### 8.1. Сначала - обычный REPL

Callback-слово - обычное слово с известным стек-эффектом. Отладьте его
ДО изготовления thunk'а:

```forth
: TCB2 ( a b -- a+2b ) 2 * + ;
1 2 TCB2 .    \ 5 - слово верно
```

Затем проверьте thunk без Windows и без DLL - ручным паттерном CALL_A
(см. шапку stdlib.f: аргументы на стек возвратов, адрес thunk'а - как
адрес функции):

```forth
' TCB2 2 MK-WINAPI-CB CONST CB2W
1 2 >R >R CB2W CALL_A DROP .        \ 5 - thunk верен (stdcall)
' TCB2 2 MK-CDECL-CB CONST CB2C
3 4 >R >R CB2C CALL_A RDROP RDROP DROP .  \ 11 - cdecl, самим снять 2 ячейки
```

### 8.2. Тестовая DLL (test/cbtest.dll)

DLL сама вызывает thunk контролируемыми аргументами по обоим соглашениям
- проверяет то, что ручной паттерн не ловит (внешний код с кадрами,
ESP-баланс, серии вызовов).

Функции DLL:
- `cbw0/1/2/3/4/8` (stdcall), `cbc0/1/2/4` (cdecl) - позвать thunk с N
  аргументами, вернуть его результат;
- `cbw2_chk` - замер ESP до/после вызова thunk'а (разность читается
  `cb_esp_diff`, должна быть 0 - ловит перепутанные соглашения и
  утечки стека);
- `cbw2_loop` - серия вызовов thunk'а в цикле (ловит деградацию
  контекста на повторах).

Генерация и сборка (из каталога test/):

```
py gen_cbtest.py        && rem пишет cbtest.d и cbtest.def САМ, в UTF-8;
                        && rem перенаправление stdout сломает кириллицу
dmd -m32 -shared cbtest.d ../dll.d cbtest.def -of=cbtest.dll
```

`../dll.d` обязателен (даёт DllMain с dll_process_attach, иначе
undefined __DllMainCRTStartup). DEF-файл задаёт явные имена экспорта
(без него DMD не экспортирует функции без атрибута export).

Прогон (из корня проекта; repl.f НЕ подключать - REPL виснет на вводе):

```
test\run_cb.bat
rem или: echo BYE | console_forth.exe heap.f strings.f console.f wincon.f test\cb_test.f
```

test/cb_test.f проверяет: оба соглашения; N = 0,1,2,3,4,8; порядок
аргументов (взвешенные суммы ловят перестановки); esp_diff = 0; серия
из 100 вызовов; вложенный Call" изнутри callback'а (CBNEST = 29);
DEPTH = 0 в конце. Ожидаемый финал: `CB-TEST OK`.

### 8.3. Типовые грабли

| Симптом | Причина |
|---|---|
| THROW 2 при исполнении слова, изготавливающего thunk | `'` в этом Форте НЕ immediate: внутри определения оно на исполнении читает ВХОДНОЙ ПОТОК. Изготавливайте thunk в интерпретации: `' W 2 MK-WINAPI-CB CONST CB`, а в определениях используйте `CB` |
| Callback отработал, после возврата из внешней функции мусор/падение | Перепутано соглашение (thunk stdcall вместо cdecl или наоборот) - ESP съехал на 4*N |
| Аргументы сдвинуты/лишние | N в фабрике не совпадает с прототипом |
| Работает с одной DLL, падает с другой | У второй функции кадр/рабочие регистры - актуальный мост это переживает (контекст из снимка); если падает - проверьте, что вызов DLL идёт через Call"/CALL_A/CALLB (снимок делается там), а не через самодельный `call` |
| THROW внутри callback'а | Не перехватывается - падение. Отлаживайте слово в REPL (п. 8.1) |

### 8.4. Дизассемблер

Для проверки того, что нагенерировала фабрика или компилятор D в DLL:

```
c:\D\mingw32\i686-w64-mingw32\bin\objdump.exe -d test\cbtest.dll
c:\D\mingw32\i686-w64-mingw32\bin\objdump.exe -p test\cbtest.dll   (таблица экспорта)
```

Thunk можно смотреть из REPL: `CB2W 16 DUMP`.

## 9. Пример: оконная процедура Windows (win.f)

```forth
\ Оконная процедура - обычное слово с контрактом WndProc
: WPH ( hwnd msg wparam lparam -- res )
    ... 2 = IF 0 EXIT THEN ... 1 ;   \ WM_DESTROY -> 0, прочим -> 1

\ Thunk изготавливается при загрузке файла (интерпретация!)
' WPH 4 MK-WINAPI-CB CONST WTHUNK

: WINOPEN ( pfn -- )   \ pfn = WTHUNK - и lpfnWndProc в WNDCLASSEX
    ... WC F.PR ! ... ;

\ Автотест: SendMessageA(WM_DESTROY) гоняет путь
\ Форт -> user32 -> thunk -> cbBridge -> WPH -> результат
: WTEST ( -- ) WTHUNK WINOPEN ... ." WTEST OK" CR ;
```

Windows зовёт WndProc синхронно из CreateWindowExA/ShowWindow/
SendMessageA/DispatchMessageA - все эти вызовы в win.f идут через
слова вызова stdlib.f, то есть через callD, то есть снимок gCbSave*
свежий в каждом случае.

Живое окно (`WIN`) по-прежнему регистрирует D-функцию wndProcD
(ячейка 15 общей таблицы, console_forth.d) - обычный легальный WndProc
без заходов в Форт; для диалога с пользователем это самый безопасный
вариант. WTHUNK-путь проверен WTEST.

## 10. Старый механизм (удалён)

До thunk'ов существовал мост **wndProcBridge** (console_forth.d):
фиксированная stdcall-точка на 4 аргумента, xt обработчика из общей
ячейки 13, снимок EBP/ESI - из ячейки 14 (GSAVE), который Форт обязан
был делать словом MSGSAVE перед каждым DispatchMessage; рядом были
D-прокси d_CallFn4 (ячейка 17) и отладочный wpcLog (ячейка 22). Всё это
**удалено**: thunk-механизм превосходит его по всем пунктам (любое N,
оба соглашения, автоматический снимок в callD/callD2, вложенные вызовы
DLL, отсутствие ручных снимков). Хроника той эпопеи - в support_forth.md
(разделы про окно, помечены как исторические).

Осталась и используется **wndProcD** (console_forth.d, ячейка 15) -
обычная D-функция WndProc без заходов в Форт: самый безопасный вариант
для живого диалога с пользователем (win.f, слово WIN).
