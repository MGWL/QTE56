> Документ собран по итогам сессии анализа `console.f`, `win.f`, `forth.d`,
> `bench.f`, `repl.f`. Формат — как в `support_forth.md`: точная локация,
> воспроизведение, причина, статус.

## 1. NUMBER: отсутствие классического разбора по BASE [ИСПРАВЛЕНО]

**Где:** `forth.d`, функция `number()` (была на базе `to!int`/`catch(Throwable)`).

**Было:** разбор чисел через D-функцию `std.conv.to!int`, с перехватом исключений
для определения "не число". Не поддерживались hex/binary ввод, система
счисления всегда десятичная независимо от контекста.

**Исправлено:**
- Добавлено поле `base` в `struct NPcb` (аналог `state`).
- Слово `BASE` (`d_BASE`/`h_BASE`) — отдаёт адрес ячейки, как `STATE`.
- Бутстрап-слова `HEX`, `DECIMAL`, `OCTAL`, `BINARY` (`N BASE !`).
- `number()` переписана на классический поразрядный разбор: знак `-`,
  префиксы `$` (hex) и `%` (binary) независимо от текущего BASE, проверка
  цифры через `digitValue()` без исключений хоста.

**Проверено:** `HEX FF .` → 255, `$FF .` → 255, `%101 .` → 5, `DECIMAL BASE @ .` → 10,
ошибочный ввод (`HEX G`, `1-2`) корректно даёт THROW -13 без порчи стека.

**Остаточный риск:** нет double-cell литералов (`1.`) — не реализовано, не входило
в задачу.

## 2. EXPECT/EINSERT: переполнение буфера, len игнорировался [ИСПРАВЛЕНО]

**Где:** `console.f`, слова `EXPECT`, `EINSERT`.

**Было:**
```forth
: EXPECT // ( addr len -- )
    DROP  EBUF ! 0 ELEN ! 0 ECUR !   \ len отбрасывается сразу!
    ...
: EINSERT ( c -- )
    ELEN @ 298 > IF DROP EXIT THEN  \ хардкод под LINEBUF (300), не под реальный буфер
```
Параметр `len` в `EXPECT` декларирован, но реально не используется — граница
вставки — зашитая константа `298`, привязанная к размеру `LINEBUF` (300 байт)
в `repl.f`. Любой вызов `EXPECT` с буфером меньше 298 байт (а в `repl.f` это
ВСЕ: `IBUF 80`, `NBUF 80`, `SBUF 80`, `ABUF 80`; в `fio.f`: `tbuf+1 254`)
не защищён — ввод длиннее размера буфера пишет в память СОСЕДНЕЙ переменной.

**Доказано на практике:** `INFO` (repl.f) — ввод 150 символов `A` в `NBUF`
(80 байт) затирал бы начало `SBUF`, расположенного в кодофайле сразу следом.

**Исправлено:**
- Добавлена переменная `ELIM` рядом с `EBUF`/`ELEN`/`ECUR`.
- `EXPECT`: `DROP` → `ELIM !` (сохраняет реальный размер буфера).
- `EINSERT`: `ELEN @ 298 >` → `ELEN @ ELIM @ 2 - >` (граница привязана
  к конкретному вызову, не к LINEBUF).

**Проверено:** ввод 150 символов в 80-байтный буфер корректно обрезается на
79 символах, соседняя переменная не затирается. `fio.f` (254-байтная граница,
255-байтный `HALLOC`) теперь тоже безопасен.

## 3. WPH: утечка стека данных во всех трёх ветках [ИСПРАВЛЕНО]

**Где:** `win.f`, слово `WPH`.

**Было:**
```forth
: WPH ( hwnd msg wparam lparam -- result )
    MQ Q.L ! MQ Q.W ! MQ Q.M ! MQ Q.H !
    MQ Q.M @ DUP 2 = OVER 16 = OR IF 1 WQUIT ! 0
    ELSE DUP 132 = IF DROP 2
    ELSE 1 THEN THEN ;
```
`DUP 2 = OVER 16 = OR` снимает только булев флаг через внешний `IF` — исходный
`msg`, продублированный `DUP`, остаётся на стеке данных во всех трёх ветках
(DESTROY/CLOSE, NCHITTEST, default). Каждый вызов `WPH` оставляет **2** значения
вместо заявленного одного (`-- result`).

**Подтверждено прямым тестом:** `0 2 0 0 WPH .S` → `[2]-> 0 2` (ожидалось `[1]-> 0`).

**Практическое следствие:** при реальном оконном message loop (десятки сообщений
на одно `CreateWindowExA`) стек данных Форта (1000 ячеек) переполнился бы
за ~500 сообщений.

**Попытки исправления, которые провалились (важно для будущих правок):**
1. `ROT`/`-ROT` для перестановки `msg` относительно флагов — требовали больше
   элементов на стеке, чем реально было (неверный расчёт глубины).
2. `>R`/`R@`/`R>` для хранения `msg` на время `IF/ELSE` — сработало НЕВЕРНО:
   `R@` в этом Форте читает `[ESP+CELL]`, рассчитывая, что между `>R` и `R@`
   нет вызовов DOES>-слов. Внутри `IF`/`ELSE` это технически безопасно
   (control-flow не трогает R-стек), НО в процессе отладки всплыл более
   фундаментальный баг №6 (см. ниже) — на момент этой попытки причина
   бага ещё не была понятна, финальное решение ушло в вариант 3.

**Финальное исправление:** читать `MQ Q.M @` заново для каждого сравнения,
не пытаясь сохранить/восстановить значение через любой из стеков:
```forth
: WPH ( hwnd msg wparam lparam -- result )
    MQ Q.L ! MQ Q.W ! MQ Q.M ! MQ Q.H !
    MQ Q.M @ 2 = MQ Q.M @ 16 = OR
    IF 1 WQUIT ! 0
    ELSE MQ Q.M @ 132 = IF 2
    ELSE 1 THEN THEN ;
```

**Проверено:** `DEPTH` до/после = 0 для всех веток (msg=2, 16, 132, 15, 0),
корректные значения результата, `WTEST OK` со стеком `[0]->` после теста.

## 4. WINOPEN: утечка одной ячейки на успешном пути [ИСПРАВЛЕНО]

**Где:** `win.f`, слово `WINOPEN`.

**Было:**
```forth
DUP HW ! 0= IF ." CreateWindowEx failed" CR EXIT THEN
HW @ 1 ShowWindow DROP
```
`DUP` дублирует hwnd для проверки `0=`. Ветка ошибки делает `EXIT` (не доходит
до конца слова), но путь "окно создано успешно" НЕ содержит `DROP` для этой
копии — каждый успешный вызов `WINOPEN` оставляет 1 лишний элемент.

**Исправлено:** добавлен `DROP` сразу после проверки на успешном пути.

**Проверено:** `WINOPEN` + `DEPTH` = 0 (было 1 до фикса), `WTEST` со стеком
`[0]->` после (было `[1]-> 38870892`, мусор от накопления утечек).

## 5. Повреждение кириллицы в win.f/console.f до U+FFFD [ВОССТАНОВЛЕНО]

**Что произошло:** во время правок №3/№4/№2 через файловый edit-инструмент
комментарии на русском в `win.f` и `console.f` оказались заменены символом
`U+FFFD` (REPLACEMENT CHARACTER) — байты физически утрачены, не просто
неверно отображались. Из 1900 кириллических символов `win.f` целыми
остались только 5 строк, написанных заново в процессе тех же правок.
`console.f` — аналогично (2040 повреждённых символов).

**Причина (гипотеза):** оригинальные файлы были в кодировке CP1251;
инструмент редактирования читал/писал их, предполагая UTF-8 — байты
кириллицы (0x80-0xFF, невалидные как UTF-8 в этом диапазоне) заменились
на replacement character уже на чтении, запись зафиксировала потерю.

**Восстановлено:** найдены целые CP1251-резервные копии в `panic/win.f`
и `panic/console.f` (0 повреждённых символов). Оба файла пересобраны:
структура и текст комментариев — из резервных копий (конвертация
CP1251→UTF-8), код — актуальный исправленный (пункты 2, 3, 4 этого
документа). Комментарий к `WPH` в `win.f` дополнительно переписан, чтобы
отражать реальную финальную архитектуру (`wndProcD`, не устаревшую идею
через D-прокси из мостового колбэка).

**Профилактика на будущее:** `AGENTS.md` требует строгого UTF-8 для
`registry/functions.csv`/`qte56.ini` — для `.f`-файлов в CP1251 аналогичного
явного требования нет, но стоит иметь это в виду при редактировании старых
`.f`-файлов любыми текстовыми инструментами. Резервные копии в `panic/`
оказались спасением — целесообразно не удалять их.

## 6. Фундаментальное ограничение: >R несовместим с DOES>-словами между парой >R...R> [ИСПРАВЛЕНО ПРЕВЕНТИВНО — R2-стек]

**Статус: архитектурная причина подтверждена; в ядре добавлен параллельный
R2-стек (>R2/R2>/R2@/R2DROP/R2+/RP2@/RP2!/D>R2/DR2>). Старые >R/R>/R@/R+/RDROP
оставлены без изменений. Новый стек — рекомендуемый путь для кода, смешивающего
DOES>-слова (VAR/CONST/FIELD) с хранением на R-стеке.**

### Как было найдено

При попытке реализовать "путь 2" (мост `wndProcBridge` + вызов `DefWindowProc`
из `WPH` через `d_CallFn4`/`CALLB`, как задокументировано нерабочим в
`support_forth.md`, раздел "ОТКРЫТО") была написана тестовая версия:

```forth
MQ Q.H @ >R MQ Q.M @ >R MQ Q.W @ >R MQ Q.L @ >R XDWP >R
17 COMMONADR@ CALLB DROP
```

Крашилось со случайными мусорными параметрами в `d_CallFn4` (проверено через
временный `printf`-лог внутри самой D-функции: `a=14619292 b=4200041 fn=0x0`
вместо реальных `hwnd/msg/wp/lp/XDWP`).

### Процесс исключения гипотез (хронология, чтобы не повторять путь)

1. **Выравнивание ESP под SSE/movaps** (та же причина, что чинили в мосте
   `wndProcBridge` по `support_forth.md`) — добавлено `and ESP,-16` перед
   `call ECX` внутри `callD2`. **Не помогло**, крash идентичен.
2. **Arity mismatch в d_CallFn4** (прокси вызывает любую функцию с фиксированной
   4-параметровой сигнатурой) — проверено на чистом D (без Форта вообще):
   вызов `IsWindowVisible` (1 параметр) через 4-параметровый прокси даёт
   access violation (callee делает `ret 4`, caller предполагал `ret 16` —
   12 байт остаются неснятыми, стек рассинхронизируется). **Это реальный
   баг класса "arity mismatch", но `DefWindowProcA` имеет РОВНО 4 параметра**,
   значит для конкретно этого случая проблема в другом. Прямой D-вызов
   `d_CallFn4(a,b,c,d,fn=DefWindowProcA)` на чистом D работает корректно.
3. **Межстрочный `>R`** — при тестировании через многострочные `.f`-файлы
   (`includedForth` вызывает `evalForth()` НА КАЖДУЮ строку отдельно)
   `>R` в одной строке и `R>` в следующей давал крash. Это реальное и
   ожидаемое ограничение (`evalForth` не гарантирует сохранность R-стека
   между вызовами — каждый вызов делает свои `push`/`pop` регистров D
   вокруг `call f_inter`), но НЕ причина оригинального бага: `WPH` —
   единое `:`-определение, исполняется в один проход `f_inter`, без
   межстрочных разрывов `evalForth`.
4. **Настоящая причина, найденная и подтверждённая изолированным тестом:**

### Причина (подтверждена)

`DOES>` в этом ядре реализован как:
```forth
: (DOES) R> R> SWAP EXECUTE ;
```
Каждый вызов любого DOES>-слова (`VAR`, `CONST`, `FIELD` на структурах,
т.е. **любая переменная, константа или поле — вообще весь пользовательский
стейт в программах на этом Форте**) САМ забирает **два** значения со стека
возврата (R-стек/ESP) как часть своей внутренней механики (адрес тела +
адрес doer-кода).

Если между пользовательским `>R` и соответствующим `R>` происходит вызов
ЛЮБОГО DOES>-слова — его внутренний `R> R>` съедает пользовательское
значение, думая, что это его служебные данные. Результат — рассинхронизация
R-стека, итоговый `jmp`/`call` по мусорному адресу (как правило, по
численному значению, которое пользователь пытался туда положить).

**Доказано минимальными изолированными тестами** (без единого упоминания
колбэков, DLL, окон):
```forth
VAR TY1
10 TY1 !
TY1 @ >R TY1 @ >R R> R> . .
\ -> Access Violation, адрес краша = значение TY1 (10 = 0x0A)

5 CONST FIVE
10 >R FIVE >R R> R> . .
\ -> Access Violation, адрес краша = значение FIVE (5 = 0x05)

1 2 3 4 >R >R >R >R R> R> R> R> . . . .
\ -> РАБОТАЕТ (простые литералы, без DOES>-слов между >R)
```

В оригинальной `WPH` именно `MQ Q.H`/`MQ Q.M`/`MQ Q.W`/`MQ Q.L` (поля
структуры, созданные через `FIELD`, то есть DOES>-слова) чередовались с
`>R` — отсюда и крash, маскировавшийся под "колбэк-специфичную проблему"
в `support_forth.md` (автор документа, по всей видимости, строил вызов
тем же способом и не докопался до истинной причины, связав симптом с
контекстом колбэка, в котором проводился тест).

### Почему это осталось нерешённым в ядре

Правка `(DOES)` затронула бы АБСОЛЮТНО ВСЕ переменные/константы/структуры
во всей кодовой базе (`stdlib.f`, `console.f`, `win.f`, пользовательские
программы) — это самый массово используемый механизм ядра. Любое изменение
без исчерпывающего регрессионного прогона всех `.f`-файлов и `test/`
несёт неприемлемо высокий риск тихой порчи поведения в местах, где
сейчас всё работает (потому что `>R` без DOES>-слов между парой работает
штатно везде, где уже используется — `stdlib.f`, `CWIN12`).

### Решение: параллельный R2-стек (реализовано в forth.d)

Вместо правки `(DOES)` добавлен **второй, независимый R-стек** на регистре
`EDI` (ранее не использовался ни одним примитивом ядра). Новые слова:

| Слово | Аналог | Назначение |
|---|---|---|
| `>R2` | `>R` | перенести со стека данных на R2-стек |
| `R2>` | `R>` | перенести с R2-стека на стек данных |
| `R2@` | `R@` | прочитать вершину R2-стека |
| `R2DROP` | `RDROP` | снять вершину R2-стека |
| `R2+` | `R+` | прибавить к вершине R2-стека |
| `RP2@` | `RP@` | адрес вершины R2-стека |
| `RP2!` | `RP!` | установить указатель R2-стека |
| `D>R2` | `D>R` | перенести две ячейки на R2-стек |
| `DR2>` | `DR>` | вернуть две ячейки с R2-стека |

Старые `>R/R>/R@/R+/RDROP/RP@/RP!` **не тронуты** — они остаются на
native `ESP`, потому что `(JOIN) R>`, `(DOES) R> R>`, `COMPILE` `R@ ... R+`
и `(BOX) R@ ... R+` читают/двигают именно native адрес возврата после
`CALL` (0xE8) в теле скомпилированного слова. Разделить эти два использования
нельзя без переписывания всей компиляции — поэтому вместо этого добавлен
параллельный стек.

**Реализация (forth.d):**
- `stSR` — новый массив `new uint[sizeStack]` (как `stSD`/`stSL`), поле
  `gpcb.csr` — вершина R2-стека (уже было зарезервировано в `NPcb`, но
  не использовалось: комментарий `// npcb.csr = ... ---> Совмещен со стеком D`).
- `EDI` — указатель R2-стека (растёт вниз, как `EBP`/`ESI`).
- `initForth` инициализирует `EDI` из `npcb.csr` рядом с `ESI`/`EBP`.
- `evalForth`/`executeForth` сохраняют/восстанавливают `EDI` (добавлен
  `push EDI`/`pop EDI` в том же порядке, что `ESI`).
- Тёплый сброс по `THROW` без `CATCH` теперь сбрасывает и `gpcb.saveEDI =
  gpcb.csr` (оба пути — `executeForth` и `evalForth`), как уже делалось
  для `saveESI`/`csc`.
- Регистрация слов: `\3>R2`, `\3R2>`, `\3R2+`, `\3R2@`, `\6R2DROP`,
  `\4RP2!`, `\4RP2@`, `\4D>R2`, `\4DR2>` (длины префиксов исправлены —
  `D>R2`/`DR2>` — 4 символа, не 3).

**Проверено (изолированно, без DOES>-слов):**
- `1 >R2 R2@ .` → 1; `1 >R2 R2> .` → 1.
- `11 22 33 >R2 >R2 >R2 R2@ . R2DROP R2@ . R2DROP R2> .` → 22, 33, 11 (LIFO).
- `1 2 D>R2 DR2> . .` → 2, 1 (семантика как `D>R`/`DR>`).
- Старые `>R/R>` не затрагиваются: `VAR TY1` + `>R`/`R>` работает как раньше.

### Важное открытие при повторной проверке репро (артефакт тестового харнеса)

При попытке воспроизвести баг №6 с корректно аллоцированными структурами
(`STRUCT CELL FIELD ... /STRUCT /Q` + `HERE /Q ALLOT CONST MQ` — идиома
из `win.f`) краш **не воспроизводится** на немодифицированном ядре:
`MQ Q.H @ >R MQ Q.M @ >R R> R> . . DEPTH .` → `10 20 0`, без AV.

Все ранее наблюдавшиеся краши с `STRUCT`/`FIELD` были артефактом
**неправильного тестового харнеса**: `VAR MQ` выделяет 1 `CELL` (4 байта),
а `Q.M`/`Q.W`/`Q.L` имеют смещения 4/8/12 и пишут/читают за пределами
`MQ`, затирая соседний кодофайл. Это давало `Access Violation`/
`Illegal Instruction`, маскирующиеся под баг №6.

**Вывод:** баг №6 реален как архитектурное ограничение (описан выше), но
на текущем билде с корректным использованием `STRUCT`/`FIELD` он не
проявляется. R2-стек — превентивная защита для кода, который смешивает
DOES>-слова с хранением на R-стеке, и безопасная альтернатива `>R`/`R>`.

### Безопасный обход (рекомендуется, НЕ требует изменений ядра)

Правило: **собрать все значения на стеке ДАННЫХ сначала (включая все
обращения к переменным/константам/полям), и только потом класть на R
одной непрерывной группой `>R`×N без единого DOES>-вызова между ними.**

Пример безопасной версии фрагмента `WPH` (путь 2, вызов `DefWindowProc`):
```forth
MQ Q.H @ MQ Q.M @ MQ Q.W @ MQ Q.L @ XDWP   \ сначала ВСЕ значения на стек данных
>R >R >R >R >R                              \ потом >R идут подряд, без DOES> между ними
17 COMMONADR@ CALLB DROP
```
Это именно та причина, по которой `CWIN12` (12 параметров, `>R`×12 подряд)
работает без проблем — там все 12 значений вычисляются заранее и лежат
на стеке данных единым блоком перед цепочкой `>R`.

**Статус пути 2 после этого открытия:** не протестирован повторно с
исправленным порядком (сессия анализа была прервана на этапе диагностики,
исправление `WPH` для пути 2 не применено — текущий рабочий `win.f`
использует финальную архитектуру `wndProcD`, путь 2 остаётся
экспериментальным).

### Повторная проверка (сессия 2026-10-02): репро не воспроизвелось напрямую — найден артефакт харнеса

При попытке повторно воспроизвести баг перед правкой ядра обнаружилось, что
наивные примеры выше (`VAR TY1`, `CONST FIVE`) **не крашатся** на текущей
сборке — `TY1 @ >R TY1 @ >R R> R> . .` печатает `10 10` без ошибок. Причина:
`(DOES)` для простых `VAR`/`CONST` делает ровно один `EXECUTE` без доп. слов
после — риск коллизии чисто теоретический для одноуровневых DOES>-слов на
практике просто не всегда проявляется (зависит от того, что `(DOES)` само
успевает снять свои 2 ячейки раньше, чем пользовательский `R>` их прочтёт).

Баг стабильно воспроизвёлся на `FIELD`-аксессорах (`(DOES) @ +` — два
дополнительных слова после диспетчеризации), но ТОЛЬКО при использовании
сломанного тестового харнеса: `VAR MQ` (выделяет 1 CELL) + `STRUCT ... FIELD
... DROP` (без `/STRUCT`/`ALLOT`) — в этом случае `Q.M`/`Q.W`/`Q.L` (смещения
4/8/12) читают/пишут ЗА пределами 4-байтного `MQ`, затирая соседние байты
кодофайла. Это самостоятельный баг тестового кода, а не ядра.

**Проверено на правильной идиоме** (как в `win.f`): `STRUCT CELL FIELD Q.H
CELL FIELD Q.M ... /STRUCT /Q` + `HERE /Q ALLOT CONST MQ` — тогда
`MQ Q.H @ >R MQ Q.M @ >R MQ Q.W @ >R MQ Q.L @ >R R> R> R> R> . . . .` (внутри
`:`-определения, 4 разных `FIELD` вперемешку с `>R`/`R>`) печатает корректные
значения, `DEPTH` после = 0, **без крашей** — на немодифицированном ядре.

Таким образом архитектурная причина (общий ESP у `>R`/`R>` и у `(DOES)`/
`COMPILE`/`(BOX)`) подтверждена чтением кода и остаётся валидной как
потенциальный риск, но получить стабильный краш на корректно написанном
Forth-коде в рамках этой сессии не удалось — вероятно, нужны более глубокая
вложенность DOES>-вызовов или другой паттерн, не предпринятый в этой сессии.
**Фикс сделан превентивно**, не дожидаясь более опасного репро на реальном
коде (`WPH`/`CALLB`, путь 2).

### Фикс: отдельный R2-стек на регистре EDI (реализовано)

Вместо правки `(DOES)`/`COMPILE`/`(BOX)` (вариант 2 ниже, высокий риск) и
вместо чистого линтера (вариант 1, не исправляет, только предупреждает)
выбран третий путь: **новый, параллельный набор слов на отдельном от ESP
стеке**, не трогающий существующие `>R`/`R>`/`R@`/`R+`/`RDROP`/`RP@`/`RP!`.

**Почему не отдельный "чистый" R-стек для существующих `>R`/`R>`:** первая
попытка (отвести именно `>R`/`R>`/`R@`/`R+`/`RDROP` на новый регистр,
оставив имена без изменений) немедленно сломала `(JOIN)`, `(DOES)`,
`COMPILE`, `(BOX)" — все они написаны в предположении, что `R@`/`R>`
читают РЕАЛЬНЫЙ native-адрес возврата, положенный инструкцией `CALL`
(0xE8) в тело слова при компиляции (`: (JOIN) R> LATEST @ TOKEN! ;`,
`: COMPILE R@ TOKEN@ TOKEN R+ COMPILE, ;` и т.д.) — старые `>R`/`R>` это
не "пользовательский scratch-стек", а часть механизма инлайн-операндов
компилятора. Переименование словосочетания без переноса реализации было
единственным рабочим вариантом.

**Реализация (`forth.d`):**
- Поле `csr` в `NPcb` (было зарезервировано, но не использовалось —
  комментарий `npcb.csr = ... ---> Совмещен со стеком D`) — теперь реально
  хранит вершину нового стека `stSR` (отдельный `uint[sizeStack]`, как `stSD`/`stSL`).
- Регистр-указатель — `EDI` (был свободен: только `saveEDI`-плейсхолдер в
  `NPcb`, никакое слово его не использовало как scratch).
- `initForth()` инициализирует `EDI` из `npcb.csr` при старте.
- `evalForth()`/`executeForth()` сохраняют/восстанавливают `EDI` вместе с
  `ESI`/`EBP` на границе D↔Forth (`push/pop EDI` в общем списке регистров).
- Тёплый сброс по `THROW` без активного `CATCH` в обоих местах
  (`evalForth`/`executeForth`) теперь дополнительно делает
  `gpcb.saveEDI = gpcb.csr` (аналогично `gpcb.saveESI = gpcb.csc`) — иначе
  R2-стек после непарного THROW остался бы в "грязном" состоянии.
- Новые слова (регистрация через `CreateVocItem`, длины имени проверены):
  `>R2` ( d:n -- r:n ), `R2>` ( r:n -- d:n ), `R2@` ( r:n -- r:n d:n ),
  `R2DROP` ( r:n -- ), `R2+` ( r:a d:b -- r:a+b ), `RP2@`/`RP2!` (адрес
  вершины R2-стека), `D>R2`/`DR2>` (парные версии, семантика идентична
  старым `D>R`/`DR>`, но на `EDI`).

**Проверено изолированно** (без FIELD/DOES>, чтобы отделить от описанной
выше находки про сломанный харнес): `1 >R2 R2@ .` → 1; `11 22 33 >R2 >R2
>R2 R2@ . R2DROP R2@ . R2DROP R2> .` → 33, 22, 11 (корректный LIFO);
`1 2 D>R2 DR2> . .` → 2 1 (как у `D>R`/`DR>`). Старые `>R`/`R>`/`(JOIN)`/
`(DOES)`/`COMPILE`/`(BOX)` не затронуты — компиляция без ошибок, слова
продолжают работать как раньше.

**Рекомендация по использованию:** в новом коде, где значения, временно
хранимые между DOES>-словами (`FIELD`/`VAR`/`CONST` обращениями), нужно
"пронести" через управляющую конструкцию (`IF`/`ELSE`/цикл) — использовать
`>R2`/`R2>`/`R2@`/`R2DROP` вместо `>R`/`R>`/`R@`/`RDROP`. Старые слова
оставить для существующего кода и для случаев, где `>R`/`R>` используется
как часть компиляторных идиом (`COMPILE`, `(BOX)`, пользовательские
DOES>-определения) — туда R2 не подходит, т.к. там именно НУЖЕН native
адрес возврата.

### Рекомендация по изменению архитектуры (альтернативы, не выбраны)

Если в будущем понадобится более глубокое решение, варианта два (оба
менее предпочтительны, чем реализованный R2-стек):

1. **(Низкий риск) Статический анализ/линтер:** добавить в `qte class`-подобный
   инструмент (или отдельный скрипт) проверку `.f`-файлов на паттерн
   "DOES>-слово между `>R` и `R>` в пределах одного `:`-определения" —
   не меняет ядро, предотвращает повторение бага на этапе разработки.
   Дополняет R2-стек: подсказывает, где `>R` надо заменить на `>R2`.
2. **(Высокий риск, не рекомендуется без явной необходимости) Правка `(DOES)`:**
   развести механизм передачи "адрес тела + адрес doer" с пользовательским
   R-стеком — например, через отдельную фиксированную ячейку в `NPcb`
   (аналогично `gExecuteRet`) вместо `R> R>`. Требует полного регрессионного
   прогона всех `.f`-файлов и `test/` (163 файла), потому что `DOES>`
   используется ядром (`CONST`, `VAR`, `FIELD`) без исключений. Отдельный
   R2-стек достигает той же цели (безопасное временное хранение поверх
   DOES>-слов) без этого риска.
