# План исправления ошибок интерпретатора forthD

> Статус: ошибки 1 (THROW), 2 (NUMBER), 6 (?EXIT) и 7 (константы) ИСПРАВЛЕНЫ.
> Дополнительно исправлены вскрывшиеся бутстрап-определения `?COMP`/`?EXEC`
> (было `STATE NOT`/`STATE IF`, стало `STATE @ NOT`/`STATE @` — STATE отдаёт адрес).
> Также исправлена ошибка в stdlib.f: ветки `_-Call"` для 0 параметров (типы 1 и 2)
> не имели финального DROP — на стеке оставался дубль результата, который CALL_A
> кладёт и в EAX, и в память. Добавлен DROP по образцу веток с параметрами.
> Изменены размеры: TIB = 2048 байт (было 1000), кодофайл = 160 Кбайт
> (sizeCodeFile = 40960 ячеек, было 30000).
> Ошибки 3, 4, 5 остаются открытыми.

Файл предназначен для чтения ИИ-агентом. Здесь собраны точные места, текущий код и конкретные действия, чтобы не перечитывать весь проект.

## Контекст проекта (минимум для работы)

- Каталог: `H:\qte56\arch_new\forth`
- `forth.d` (~2190 строк) — модуль `forth`, ядро интерпретатора. 32-разрядный D с naked asm. Компилируется **только** `dmd -m32` (naked asm). Шитый код: слова компилируются в x86 (CALL=0xE8 через `COMPILE,`, JMP=0xE9 через `JUMP,`). Вершина стека данных в EAX, стек данных на EBP, стек возвратов = нативный ESP, локальный стек на ESI.
- `console_forth.d` — консольный main (REPL), создан недавно. Сборка: `dmd -m32 forth.d console_forth.d -ofconsole_forth.exe`
- `stdlib.f` — библиотека на Форте, грузится из main через `includedForth("stdlib.f")`.
- `console5_forthd.d`, `forthdll.d` — GUI (QtE5) и DLL варианты, для консольной задачи не нужны.
- Контекст интерпретатора: `struct NPcb gpcb` (forth.d:90). Ключевые поля: `csd` (дно стека данных), `saveEBP` (текущий указатель стека данных), `csc` (вершина локального стека), `here`, `akdf` (начало кодофайла), `Tib`, `In`, `dlTib`, `state`, `latest`, `context`.
- Константы: `CELL=4`, `sizeCodeFile=40960` ячеек (160 Кбайт), `sizeStack=1000` ячеек, `tib` — `ubyte[2048]` (forth.d:45-47, 94).
- Стеки выделены в `initForth()` (forth.d:1607): `stSD = cast(pp)(new uint[sizeSt])`, `npcb.csd = stSD + sizeSt - 1` (стек растёт вниз, дно = старший адрес). Кодофайл на Windows — `VirtualAlloc(PAGE_EXECUTE_READWRITE)` (forth.d:1612-1618).
- Вход: `evalForth(string)` (forth.d:1552) копирует строку в `tib` и вызывает `f_inter` (цикл интерпретатора, forth.d:1975).
- Проверка любого исправления: `dmd -m32 forth.d console_forth.d -ofconsole_forth.exe` затем `printf '...\nBYE\n' | ./console_forth.exe`. Базовый smoke-тест: `2 3 +` → стек `[1]-> 5`; `: SQ DUP * ;` затем `5 SQ .` → печатает 25.

## Ошибка 1. THROW не прерывает выполнение и не восстанавливает стеки [ИСПРАВЛЕНО]

> Исправлено настоящим CATCH/THROW (см. раздел «CATCH/THROW» ниже):
> THROW разматывает native-вызовы, восстанавливает EBP/ESI и либо
> приземляется в ближайший CATCH, либо abort'ит строку до границы
> evalForth/executeForth с тёплым сбросом. Ограничение: определение,
> недостроенное в момент THROW, остаётся в словаре.
> Исторический план (тёплый сброс через gThrowCode) — ниже, он стал частью
> реализации (обработка случая «CATCH нет»).

**Где:** `h_THROW` / `f_THROW`, forth.d:1430-1436.

**Текущий код:**
```d
private void h_THROW(int n) {
	writeln();
	writeln("[", n, "]", " THROW - error, this mast find ...");
}
private void f_THROW() {
	asm {	naked;	call h_THROW;  jmp h_DROP;	 }
}
```

**Проблема:** THROW только печатает код и продолжает выполнение потока. Стеки (данных/возвратов) не сбрасываются, `STATE` не сбрасывается в интерпретацию. После THROW система в неопределённом состоянии. Слово `?COMP` (forth.d:1854: `: ?COMP STATE NOT IF 1 THROW THEN ;`) и `?EXEC` полагаются на THROW.

**План исправления (минимальный, без полной семантики CATCH):**
1. В `h_THROW(int n)`: если n==0 — просто вернуться (по канону `0 THROW` — no-op). Если n!=0 — напечатать код и выполнить «тёплый» сброс: восстановить указатели стеков из контекста.
2. Сброс делается в D после возврата из asm — самый безопасный путь: ввести модульный флаг `private __gshared int gThrowCode;`. `h_THROW` при n!=0 пишет `gThrowCode = n;` и печатает сообщение.
3. В `evalForth(string)` (forth.d:1552) после asm-блока и обновления `gpcb` (после строки ~1599) добавить:
```d
	if(gThrowCode != 0) {
		gThrowCode = 0;
		// Сброс стека данных: вернуть EBP на дно
		gpcb.saveEBP = cast(pp)(cast(uint*)gpcb.csd + 1); // дно + 1 ячейка, как в SP_set
		gpcb.state = cast(pp)0;      // вернуться в режим интерпретации
	}
```
   Точное значение дна смотреть по `SP_set` (forth.d:638-644): `lea EBP,[EAX+CELL]`, где EAX=`csd`. Значит дно-EBP = `csd + CELL`. Проверить опытом: после `BYE`-цикла пустой стек показывает `[0]->`.
   Стек возвратов (ESP) сбрасывать из D нельзя — но он самовосстанавливается при выходе из `f_inter`, т.к. возвраты из CALL снимают адреса. Проблема только если THROW случился в глубокой вложенности: тогда оставшиеся адреса на ESP снимутся по RET при выходе из `f_inter` — это безопасно.
4. Локальный стек (ESI): сохранить в `gpcb` поле уже есть `saveESI` — сбросить `gpcb.saveESI = gpcb.csc` (вершина локального стека, как в `LP_set`, forth.d:683: ESI = значение csc).

**Важно:** полный сброс ESP невозможен из D, поэтому при глубокой вложенности THROW выполнение текущей строки продолжится после слова THROW (поведение «печать + продолжить» сохраняется внутри строки, но состояние между строками REPL будет чистым). Задокументировать это ограничение комментарием.

**Проверка:** `F> : T 1 THROW ;` затем `T` → печать `[1] THROW...`, следующая строка `2 3 +` → `[1]-> 5` (стек чист). И `?EXEC` в интерпретации: `F> ?EXEC` → `[2] THROW`.

## Ошибка 2. NUMBER: неизвестное слово молча становится числом 0 [ИСПРАВЛЕНО]

> Как исправлено на самом деле: план ниже выполнен (gNumberOk, d_numberOk, h_NUMBER
> кладёт число под флаг в EAX), НО этого оказалось мало: путь ошибки в f_inter (метка m2)
> по конструкции оставляет указатель стека на 1 ячейку ниже (фантомная ячейка - в оригинале
> она и была "молчаливым нулём"). Поэтому в f_inter выход по ошибке изменён:
> после `call h_DROP` (сброс флага) вместо `je ms` стоит `jne m4`, а по ветке ошибки
> добавлен ещё один `call h_DROP; jmp ms` - он снимает фантом и восстанавливает
> указатель стека. Проверено: серия неизвестных слов не растит стек.

**Где:** `number()` (forth.d:2027-2039), `h_NUMBER()` (forth.d:2040-2047), вызов из `f_inter` (метка `m2`, forth.d:2004-2021).

**Текущий код:**
```d
private int number(ps str) {
	int rez = 0;
	try {
		rez = to!int(to!string(str+1));
	}
	catch(Throwable) {
		writeln("Error conv [", to!string(str+1) ,"] --> Integer");
	}
	return rez;
}
private void h_NUMBER() {
	asm {	naked;
		call number;
		jmp f_TRUE;   // <-- ВСЕГДА возвращает TRUE, даже при ошибке разбора
	}
}
```

**Проблема:** при неудаче разбора печатается ошибка, но `h_NUMBER` всё равно возвращает TRUE и на стек кладётся 0. Опечатка в имени слова не прерывает выполнение, а вносит мусорное 0 на стек/в компиляцию.

**План исправления:**
1. `number()` должен возвращать признак успеха. Простейший способ без изменения соглашений asm: модульная переменная `private __gshared int gNumberOk;`. В `number()`: успех → `gNumberOk = 1`, ошибка → `gNumberOk = 0`.
2. В `h_NUMBER` заменить `jmp f_TRUE` на выбор по `gNumberOk`:
```d
private int d_numberOk() { return gNumberOk; }
private void h_NUMBER() {
	asm {	naked;
		call number;			// EAX = значение (или 0)
		push EAX;				// спасти значение
		call h_DUP;				// старое EAX на стек (значение)
		pop EAX;				// ... проверить порядок опытом!
		call d_numberOk;		// EAX = флаг
	}
	// далее нужна логика: стек должен получить [значение] [флаг]
}
```
   Тонкость: соглашение «TOS в EAX». Правильная последовательность: после `call number` в EAX значение. Надо: положить значение на стек (оно станет под-вершиной), а в EAX вернуть флаг. Код:
```d
private void h_NUMBER() {
	asm {	naked;
		call number;			// EAX = число или 0
		mov EBX, EAX;			// EBX = число (EBX свободен в этом контексте — проверить, что f_inter его не использует между m2 и je ms; использует ECX)
		call d_numberOk;		// EAX = 0/1
		lea EBP, [EBP-CELL];	// push числа на стек данных
		mov [EBP], EBX;
		ret;
	}
}
```
   Внимание: в `f_inter` после `call h_NUMBER` стоит `mov ECX,0; cmp EAX,ECX; call h_DROP; je ms` (forth.d:2008-2011) — флаг снимается со стека из EAX через h_DROP. Значит контракт: EAX=флаг, под ним значение. Приведённый код это выполняет.
3. Поведение при ошибке: флаг 0 → `je ms` → слово просто пропускается (ошибка уже напечатана из `number()`). Это соответствует текущему комментарию `je ms; // ----> ошибка прочто пропустив в потоке`.
4. Стилистически лучше сообщение об ошибке сделать «не найдено слово [X]», т.к. это основной случай.

**Проверка:** `F> NONEXIST 5 +` → печать ошибки, стек пуст `[0]->`. `F> 42` → `[1]-> 42`. `F> -17` → `[1]-> -17`.

## Ошибка 4. Нет контроля переполнения кодофайла (HERE за границей)

**Где:** `d_ALLOT(int n)`, forth.d:1116:
```d
private void d_ALLOT(int n) {	gpcb.here = gpcb.here + n; }
```
Конец кодофайла: `gpcb.akdf + sizeCodeFile` ячеек (см. `adr_endKDF()`, forth.d:66). Все продвижения HERE идут через ALLOT (проверить grep-ом `gpcb.here =` — прямые присвоения в `initForth`, `CreateVocItem` (forth.d:2123+), `h_createST` (forth.d:2062-2079) — они НЕ через ALLOT!).

**Проблема:** HERE молча уходит за пределы VirtualAlloc-области (40960*4 = 160 Кбайт) → Access Violation при записи или EXECUTE.

**План исправления:**
1. Добавить проверку в `d_ALLOT`:
```d
private void d_ALLOT(int n) {
	gpcb.here = gpcb.here + n;
	if(gpcb.here >= cast(pb)adr_endKDF())
		writeln("! ALLOT: HERE за границей кодофайла (", cast(void*)gpcb.here, " >= ", adr_endKDF(), ")");
}
```
2. Прямые присвоения `gpcb.here = gpcb.here + N` в `CreateVocItem` и `h_createST` либо оставить (они двигают HERE на байты имён, объём мал), либо обернуть в ту же проверку — вынести её в `private void checkHere()` и вызывать из обоих мест. Минимальный вариант: только `d_ALLOT`, т.к. это основной канал роста.

**Проверка:** определить в цикле много слов или `1000000 ALLOT` → предупреждение.

## Ошибка 5. INCLUDED выполняет файл построчно — не работают многострочные определения

**Где:** `h_INCLUDED`, forth.d:2171-2175:
```d
private void h_INCLUDED(ps adr) {
	string s = to!string(adr);
	File f1 = File(s, "r"); foreach(line; f1.byLine()) evalForth(cast(string)line);
}
```

**Проблема:** каждая строка — отдельный вызов `evalForth`. Определение `: FOO ... ;` на нескольких строках разваливается (STATE остаётся «компиляция» между строками, но хуже: комментарий `//` гасится только до конца строки, и парсер HERE-токена (`h_word` пишет токен по HERE) между строками конфликтует с компиляцией). Классическое решение — REFILL, но это большая переделка.

**План исправления (простой, сохраняющий архитектуру):**
1. Читать файл целиком: `string content = readText(s);` (импорт `std.file: readText`).
2. Склеить строки через пробел, но **уважая комментарии** `//` и `\`: в этой системе `//` определён как «гасить до конца TIB» (`TIB @ DLTIB + <IN !`, forth.d:1822). Если склеить строки, комментарий погасит весь остаток файла. Поэтому склейка = для каждой строки: отрезать всё после `//` (и после `\` в позиции начала лексемы — но `\` используется и как слово? В словаре есть `\` — да, forth.d:1822), затем trim, затем добавить в буфер с пробелом.
3. Ограничение: TIB всего 2048 байт → склеенный файл не влезет. Поэтому склеивать **кусками**: накапливать строки в буфер до тех пор, пока не встретится завершитель определения или буфер не достигнет ~2000 байт, затем `evalForth(buf)`. Простейший рабочий критерий завершения: буфер содержит `;` на границе лексемы ИЛИ строка не открывает определение. Ещё проще и надёжнее: накапливать до `;` или до не-`:` строки:
```d
private void h_INCLUDED(ps adr) {
	import std.file: readText;
	import std.string: indexOf, strip, splitLines;
	string content = readText(to!string(adr));
	string buf;
	foreach(line; content.splitLines()) {
		string s = line;
		auto p = s.indexOf("//");
		if(p >= 0) s = s[0 .. p];
		s = strip(s);
		if(s == "") continue;
		bool inColon = buf.length > 0;  // накапливаем внутри : ... ;
		buf ~= (buf.length ? " " : "") ~ s;
		if(!inColon && !s.startsWith(":")) { evalForth(buf); buf = null; continue; }
		if(s.endsWith(";")) { evalForth(buf); buf = null; }
	}
	if(buf.length) evalForth(buf); // незакрытое определение — отдать как есть, ошибка всплывёт
}
```
   Импорт `std.string: startsWith, endsWith`. ВНИМАНИЕ: лимит TIB 2048 байт — многострочное определение длиннее ~2000 символов всё равно не влезет; после исправления ошибки 3 будет обрезка с предупреждением. Задокументировать лимит.
4. Краевой случай: строка `: FOO ... ;` в одну строку — startsWith(":") и endsWith(";") → сработает обе ветки по порядку: сначала `!inColon && !startsWith` — ложь (startsWith есть), затем endsWith(";") → eval. Порядок проверок в коде выше это покрывает.
5. Строки-строки с `"` внутри определений (S" ... ") — склейка пробелами безопасна, т.к. разделитель лексем — пробел.

**Проверка:** создать тестовый файл:
```
: МНОГО   // комментарий
  DUP
  *
;
7 МНОГО .
```
`includedForth` этого файла → печатает 49. Регрессия: `console_forth.exe test.f` и `stdlib.f` должны грузиться как раньше.

## Ошибка 6. Сломано слово ?EXIT (f_Q_EXIT)

**Где:** forth.d:220-230:
```d
private void f_Q_EXIT() {
	asm {		naked;
		or EAX,EAX;
		mov EAX,dword ptr SS:[EBP];
		lea EBP,[EBP+CELL];
		jz M1;
		lea ESP,[ESP];      // <-- пустышка, возврат не происходит
M1:		ret;
	}
}
```

**Проблема:** если флаг != 0, слово должно сделать EXIT (снять адрес возврата со стека возвратов и выйти из текущего слова). Сейчас `lea ESP,[ESP]` — no-op, и `ret` возвращает в текущее слово в любом случае.

**План исправления:**
```d
	jz M1;
	pop EDX;            // снять адрес возврата = EXIT из слова
M1:	ret;
```
(по образцу `f_EXIT`, forth.d:212-216: `pop EDX; ret;`).
Проверить, что слово вообще зарегистрировано в словаре: grep `?EXIT` в списке `CreateVocItem` — в WORDS его нет (см. вывод 170 слов). Значит либо добавить `CreateVocItem(cast(char*)"\5?EXIT".ptr, cast(pp)&f_Q_EXIT, &gpcb.context);` рядом с EXIT (forth.d:1673), либо удалить мёртвый код. Рекомендация: исправить и зарегистрировать.

**Проверка:** `: T ?EXIT 99 . ;  0 T 1 T` → печатает 99 только один раз (при 0).

## Ошибка 7 (косметика, по желанию). Константы закодированы байтами инструкций [ИСПРАВЛЕНО]

> Как исправлено на самом деле: все семь слов (`f_CFL`, `f_TOKEN`, `f_CELL`,
> `f_REF`, `f_TRUE`, `f_FALSE`, `f_BL`) переведены на прямую запись константы:
> `call h_DUP; mov EAX, значение; ret`. Перед заменой каждое значение сверено
> декодированием байтов после `call f_s_CONST_s` (он читает dword по адресу
> возврата): CFL=5, TOKEN=5, CELL=4, REF=4, TRUE=-1, FALSE=0, BL=32 — совпало
> с документацией. Заодно исправлен ошибочный комментарий у f_FALSE.
> Побочный эффект: `f_s_CONST_s` (forth.d:444) стал мёртвым кодом — вызывающих
> не осталось (пользовательские константы строятся через `(CREATE)`+`DOES> @`),
> в словаре `(CONST)` не зарегистрирован. Оставлен на месте, можно удалить.
> Проверено пользователем: сборка и работа подтверждены.
> Историческое описание и план — ниже.

**Где:** `f_CFL` (410), `f_TOKEN` (419), `f_CELL` (530), `f_REF` (539), `f_TRUE` (1248), `f_FALSE` (1256), `f_BL` (1264).

Пример `f_TRUE`:
```d
private void f_TRUE() {
	asm {		naked;
		call f_s_CONST_s;
		di 0xFFFFFFFF;      // данные, маскирующиеся под код: (CONST) читает этот dword
	}
}
```
Работает (прочитанный dword = -1), но `f_CFL`/`f_TOKEN` используют `add EAX,0x9D000000` (байты 05 00 00 00 9D → dword 0x00000005 = значение 5), `f_CELL` — `add AL,0; add byte ptr DS:[EAX],AL` (04 00 00 00 → 4). Хрупко: «чистка мусора» сломает значения.

**План:** заменить на прямую запись константы, по образцу `h_osname` (forth.d:1302-1308):
```d
private void f_TRUE() {
	asm {		naked;
		call h_DUP;
		mov EAX, -1;
		ret;
	}
}
```
Аналогично: FALSE=0, BL=32, CELL=4, REF=4, CFL=5, TOKEN=5. Перед заменой каждого слова сверить текущее фактическое значение (декодировать байты первой инструкции после `call f_s_CONST_s`) — значения выше уже декодированы, но перепроверить ассемблерным листингом (`dmd -m32 -c` + objdump) или отладчиком. Не менять всё скопом без проверки: от этих констант зависит компиляция ссылок.

**Проверка:** `F> CELL .` → 4, `TRUE .` → -1, `BL .` → 32. Плюс полный smoke-тест и `test.f`.

# Приложение. Работа с DLL из Форта (stdlib.f)

Механизм вызова функций из динамических библиотек. Реализация: `stdlib.f` (слова
`Lib"`, `_-Call"`), опирается на примитивы ядра `forth.d`: `LOADLIBRARYA` / `GPADRESS`
(Windows, = LoadLibraryA/GetProcAddress), `DLOPEN` / `DLSYM` (Linux), `CALL_A`
(asm-слово `callD`, forth.d:~1067 — выполняет вызов по адресу).

**ВАЖНО:** интерпретатор 32-разрядный, поэтому загружаемые DLL тоже должны быть
32-разрядными. Системные библиотеки (kernel32.dll, msvcrt.dll и т.п.) на 64-битной
Windows подставляются автоматически в 32-битном виде через WOW64.

## Слова

| Слово | Стек | Назначение |
|---|---|---|
| `Lib"` | ( `"имя.dll"` имя -- ) | Создать слово библиотеки (пока без загрузки) |
| `LibraryLoad` | ( 1 -- , константа) | Параметр для слова библиотеки: загрузить DLL и разрешить адреса всех зарегистрированных функций |
| `Library@` | ( 2 -- , константа) | Параметр для слова библиотеки: выдать адрес структуры библиотеки |
| `CDECL-Call"` | ( Alib Npar `"f"` имя -- ) | Создать слово вызова функции, конвенция cdecl |
| `WINAPI-Call"` | ( Alib Npar `"f"` имя -- ) | Создать слово вызова функции, конвенция stdcall (WINAPI) |
| `GADR-Call"` | ( Alib Npar `"f"` имя -- ) | Слово кладёт на стек адрес функции, не вызывая её |
| `CDECL-Call-N"` | -- | Тип 9: отладочная ветка, печатает 5 ячеек стека |
| `ASCIIZ"` | ( `"строка"` -- Astrz ) | Вставить строку с нулём в конце в кодофайл |

## Порядок действий (КРИТИЧНО!)

1. `Lib"` — создать слово библиотеки.
2. `Library@ <lib> Npar CDECL-Call"|WINAPI-Call" "ИмяФункции" ИмяСлова` — создать
   слова вызова для КАЖДОЙ нужной функции. Слово встаёт в связанный список библиотеки.
3. `LibraryLoad <lib>` — загрузить DLL и пройти по списку, разрешив адреса функций
   через GetProcAddress.
4. Вызывать: `арг1 ... аргN ИмяСлова` — на стеке результат.

Если сделать `LibraryLoad` ДО регистрации функций (шаг 3 раньше шага 2), адреса
остаются 0 и вызов падает по Access Violation. Новые функции можно добавлять и после
загрузки, но тогда `LibraryLoad` надо повторить.

Порядок аргументов: как в C — `750 300 Beep` = `Beep(750, 300)`.

## Примеры (проверены в консольном варианте)

```
// WINAPI (stdcall), 0 параметров
Lib" kernel32.dll" k32
Library@ k32 0 WINAPI-Call" GetTickCount" GetTickCount
LibraryLoad k32
GetTickCount .            // число миллисекунд с загрузки ОС

// WINAPI, 2 параметра
Library@ k32 2 WINAPI-Call" Beep" Beep
LibraryLoad k32           // повторно, т.к. Beep добавлен после первой загрузки
750 300 Beep .            // Beep(750 Гц, 300 мс) -> 1

// CDECL, 1 параметр
Lib" msvcrt.dll" crt
Library@ crt 1 CDECL-Call" abs" myabs
LibraryLoad crt
-42 myabs .               // 42
```

## Структуры данных (из комментариев stdlib.f)

Библиотека (`Lib"`):
```
+0  CELL  адрес загруженной DLL (HMODULE), 0 пока не загружена
+4  CELL  указатель на голову списка слов функций (0 = пусто)
+8  ...   имя библиотеки (asciiz с байтом длины)
```

Вызов функции (`_-Call"`):
```
+0   CELL  адрес функции (заполняет LibraryLoad)
+4   CELL  количество входных параметров
+8   CELL  адрес следующей структуры в списке библиотеки (0 = последняя)
+12  CELL  тип вызова: 0=GADR, 1=CDECL, 2=WINAPI, 9=отладка
+16  ...   имя функции (asciiz с байтом длины)
```

Созданное слово вызова хранит в поле данных адрес своей call-структуры;
`DOES> @` его извлекает и диспетчеризует по типу и числу параметров (0..4).

## Как работает вызов (для отладки)

- Параметры кладутся на НАТИВНЫЙ стек словом `>R` (стек возвратов = ESP) в порядке
  «последний параметр первым» — так что C-функция видит их как обычно.
- `CALL_A` (callD в forth.d): адрес функции в ECX, адрес возврата прячется на
  L-стек (`SL_toL`), вызов `call ECX`, результат из EAX возвращается как TOS.
- Очистка нативного стека: CDECL — вызывающий (по `RDROP` на каждый параметр),
  WINAPI — сама функция (RDROP нет).
- `CALL_A` оставляет результат ДВАЖДЫ: в EAX и в памяти стека. Поэтому каждая ветка
  `_-Call"` заканчивается финальным `DROP`, снимающим дубль (ранее веток 0 параметров
  его не было — исправлено, см. статус выше).
- `IF=W` / `IF=L` ( forth.d:~1850) — условная компиляция по ОС: W=Windows, L=Linux
  (сравнивают `OSNAME` с 87/76). В stdlib.f переключают LoadLibraryA/dlopen.

## Диагностика ошибок

- `Error load DLL <имя>` — LoadLibraryA вернул 0 (нет файла или DLL 64-разрядная).
- `Error find function: <имя>` — GetProcAddress вернул 0 (опечатка, регистр важен;
  для stdcall-функций в некоторых DLL имена декорированы: `_Beep@8`).
- Access Violation при вызове — адрес функции 0: либо LibraryLoad до регистрации,
  либо функция не найдена (см. строку выше AV).

## REPL на самом Форте (repl.f)

Запуск: `console_forth.exe console.f wincon.f repl.f` (порядок важен).
console_forth.d ДО загрузки файлов делает `setCommonAdr(10, &evalC)`, а после
загрузки выполняет `evalForth("REPL")`. Если repl.f не загружен — печатается
«Не найдено слово [REPL]» и работает старый D-цикл (fallback).

- `evalC` (console_forth.d) — `extern(C) int evalC(char*)`: выполняет строку
  через evalForth, СРАЗУ печатает состояние стека `writeln(showSD())` и
  возвращает микросекунды (StopWatch). repl.f вызывает его как cdecl:
  `: EVALF >R EVALD CALL_A RDROP DROP ;` (EVALD = `10 COMMONADR@ CONST`).
- Выход из REPL: слово `BYE` (`: BYE 0 _EXIT DROP ;` — exit(0) из msvcrt,
  биндинг в console.f) или EOF в пайпе (см. KEY ниже). REPL никогда не
  возвращается в вызвавший его evalForth — вложенность безопасна.

### ВАЖНО: почему печать стека нельзя делать словами Форта после EVALF

TOS пользовательского стека живёт в регистре EAX (между строками — в
`gpcb.saveEAX`), в память он сбрасывается только при ПЕРВОМ push следующей
выполняемой строки (h_DUP: `lea EBP,[EBP-4]; mov [EBP],EAX`). Кроме того,
рабочий стек самого REPL (EBP во время исполнения REPL) использует ТЕ ЖЕ
адреса памяти, что и стек пользователя (оба около `csd+4`), и слова REPL
затирают эти ячейки. Поэтому чтение `[csd-i]` словами Форта после EVALF даёт
мусор/старые значения. Единственный надёжный момент — сразу после возврата
evalForth внутри evalC (эквивалент showSD() в D-цикле).

### Многострочность

Накопление буфера НЕ нужно: `gpcb.state` сохраняется между вызовами evalC,
незакрытое `:` продолжает компиляцию со следующей строки. REPL показывает
режим промптом: `STATE @` ≠ 0 → `..>` (цвет 11), иначе `F>` (цвет 14).

### Ввод: KEY/EXPECT (console.f)

`KEY`: `0 _ISATTY IF _KEY ELSE _GETCHAR DUP 0 < IF DROP 0 _EXIT DROP THEN THEN`
— в консоли `_getch` (без эха), в пайпе `getchar`; EOF (-1) → exit(0), иначе
ожидание вечно. `EXPECT` завершается по CR(13) ИЛИ LF(10) — иначе в пайпе
строка никогда не кончится. Биндинги msvcrt: `_GETCHAR`, `_ISATTY`, `_EXIT`.

### Ловушка CONTEXT (words.f содержит ошибку!)

`CONTEXT` (d_CONTEXT, forth.d:1143) возвращает АДРЕС ПОЛЯ `gpcb.context`,
а не базу массива цепочек. Правильный обход: `CONTEXT @ I CELLS + @`.
В repl.f WORDS так и сделано. В words.f старая строка `CONTEXT I CELLS + @`
без первого `@` — при запуске даёт Access Violation (чтение имени по адресу-
указателю). Если words.f понадобится — исправить там так же.

### Проверка через пайп

`printf '2 3 +\n: SQ\nDUP *\n;\n5 SQ .\nBYE\n' | ./console_forth.exe console.f wincon.f repl.f`
Ожидание: `[1]-> 5`, промпт `..>` на строках тела SQ, `25`, завершение по BYE.
Без BYE — завершение по EOF. Цвета/курсор через пайп не проверить (SetConsoleTextAttribute
на пайпе безопасно игнорируется) — только вживую в cmd.exe (`chcp 1251`).

## Ускорение f_inter (сделано)

- Проверки STATE/IMM на каждый токен больше не заходят в Форт-слова
  (`call h_STATE; call h_getFromAdr; ...; call h_DROP` ~15-20 инструкций).
  Теперь: `cmp dword ptr gpcb.state.offsetof[gpcb], 0` и
  `cmp byte ptr gpcb.imm.offsetof[gpcb], 1` (f_inter, ~2050-2090).
  xt при этом остаётся в EAX, стек данных не трогается вообще.
- `mov ECX,0; cmp EAX,ECX` заменено на `test EAX,EAX` (3 места).
- Для прямого доступа из asm `gpcb` объявлен `__gshared` (был TLS -
  «cannot directly load TLS variable»).
- В h_DROP добавлен комментарий-контракт: только mov/lea, флаги не менять -
  f_inter делает test/cmp ДО `call h_DROP`, а je/jne ПОСЛЕ (ветка m2/NUMBER).
- Проверено: интерпретация, компиляция, IMMEDIATE (IF/ELSE/." внутри :),
  DO LOOP, NUMBER-ветки, THROW-путь, test.f, оба REPL.

## Правило моста D<->Форт (evalC/EVALF): разделяй стековые области нитей

Когда Форт-слово вызывает D-функцию, которая вызывает evalForth (вложенный
evalForth), внутренняя нить стартует с EBP/ESI из gpcb.saveEBP/saveESI -
тех же значений, с которых работает внешняя (вызывающая) нить. Области
стеков двух нитей НАКЛАДЫВАЮТСЯ:

- рабочие ячейки внешней нити затирают ячейки памяти стека данных
  пользователя (глубокие элементы портятся, TOS в saveEAX выживает - поэтому
  баг маскируется: глубина и верхний элемент правильные, нижние - мусор);
- хуже: CALL_A (callD) хранит адрес возврата в нитку на L-стеке (ESI), и
  пользовательский DO LOOP кладёт предел/индекс ровно в эту ячейку -
  после возврата ret прыгает по значению предела цикла (PC=0x5, 0xA...).

Решение в repl.f: слово REPL первым делом опускает СВОИ стеки:
`SP@ 2048 - SP! LP@ 2048 - LP!` (2КБ = 512 ячеек на каждую нить).
Строки пользователя продолжают стартовать от gpcb.saveEBP/saveESI -
области больше не пересекаются. Любой будущий мост «Форт вызывает D,
которая вызывает evalForth» обязан делать то же самое.

## Asm-версии слов цикла (сделано)

Шитые слова цикла заменены naked asm (рядом с SL_Ldrop, ~строка 1052),
регистрация через CreateVocItem в initForth, шитые варианты оставлены
комментариями в бутстрапе для понимания логики:

- `(LOOP)` = f_s_LOOP_s: inc индекса на L-стеке, знаковый cmp с пределом,
  флаг для ?BRANCH (0=продолжать, -1=выйти). Ускорение пустого цикла ~10x
  (10M итераций: 280 мс -> 26 мс).
- `(+LOOP)` = f_s_PLOOP_s: то же с шагом n со стека данных; глубина стека
  данных не меняется (шаг заменяется флагом). ОГРАНИЧЕНИЕ как у бывшей шитой
  версии: знаковое сравнение, отрицательный шаг завершает цикл сразу.
- `(DO)` = f_s_DO_s: ( предел индекс -- ) на L-стек, [ESI]=индекс, [ESI+4]=предел.
- `I` = h_I (чтение [ESI]), `J` = h_J (чтение [ESI+8], индекс ВНЕШНЕГО цикла).
  J - новое слово, раньше отсутствовало.
- Компилирующие слова DO LOOP +LOOP остались на Форте (работают 1 раз при
  компиляции, ускорять нечего).

Тесты: 0..9, отрицательный диапазон, вложенные с J, +LOOP с шагом 2,
0 0 DO - одна итерация, repl.f-набор, test.f.

## SEE - декомпилятор слов (сделано)

Вызов из консоли: `SEE имя` - печатает тело слова построчно: адрес,
имя вызываемого слова / литерал / ветвление, в конце EXIT.

Реализация: `seeC(void* xt)` в console_forth.d (extern(C), ячейка 11 общей
таблицы, setCommonAdr(11) в main ДО загрузки файлов). Слово SEE в repl.f:
`: SEE BL WORD DUP IF FIND DUP IF >R SEED CALL_A RDROP DROP DROP ELSE ...`
(два DROP: ячейка-фантом от CALL_A + void-результат seeC). Хелперы findXT
(имя -> xt через обход 256 цепочек словаря) и nameByAddr (адрес -> имя).

ЗАЩИТА ОТ КРАХА (найдено тестом `SEE SQ` на неопределённом слове):
- НЕ использовать `'` (tick): на ненайденном слове он делает THROW 3, но
  THROW только печатает "[3] THROW - error" и НЕ прерывает выполнение
  текущего слова (forth.d:1997) - SEE продолжился бы с xt=0 -> AV в seeC.
- Поэтому `BL WORD FIND` + ДВЕ проверки DUP IF: WORD возвращает 0, если
  после SEE нет слова (конец строки); FIND возвращает 0, если слова нет
  в словаре. Оба случая -> DROP + "not found".
- Дополнительно null-check в начале seeC (страховка от прямого вызова
  seeC с 0 мимо слова SEE).

Формат словарной статьи (h_createST, forth.d:2222):
`NFA -> [len][имя][0][len][imm][LFA:4][код]`, xt = nfa + *nfa + 8.
У asm-слов по xt трамплин `E9 rel32` на D-функцию; у колонок сразу тело:
цепочка `E8 rel32`, конец - голый байт 0xC3 (";" компилирует RET, не call).

КЛЮЧЕВОЙ ФАКТ для любого разбора скомпилированного кода: цель E8 бывает
ДВУХ видов - трамплин xt слова И прямой адрес D-функции. f_inter (метка
m4, forth.d:2171) компилирует литерал как `call h_s_LIT_s` напрямую через
классический COMPILE (h_COMPILE читает следующую за ним инструкцию call
как данные, сама она не выполняется). Поэтому цели разрешаются ТОЛЬКО
через словарь: xt + разрешение трамплина (xt+5+rel32).

Спецслова с inline-данными (обязательно учитывать, иначе рассинхрон):
- (LIT):    +4 байта число (h_s_LIT_s читает ячейку по адресу возврата);
- BRANCH/?BRANCH: +4 байта смещение, dest = p+5+off (f_BRANCH: pop EBX;
  add EBX,[EBX]; jmp EBX - смещение от АДРЕСА ПОЛЯ смещения);
- (BOX):    counted-строка len+2 байта (бутстрап forth.d:2000:
  `: (BOX) R@ DUP B@ 2 + R+ ;`). Кстати ." разворачивается в
  (BOX) 1+ TYPE - видно в выводе SEE;
- (CREATE): данные неизвестной длины -> SEE печатает и останавливается;
- байт 0xE9 внутри тела: хвостовой JMP в DOES>-часть -> печать и стоп.

Защиты: лимит 500 инструкций; неизвестный байт (не E8/E9/C3) - сообщение
"?? byte" и стоп (не AV). Строки вывода seeC - ASCII: console_forth.d в
UTF-8, а консоль cp1251, русские литералы из D печатаются кракозябрами.

Проверено: SEE SQ (DUP * EXIT), SEE T2 (литерал, ?BRANCH/BRANCH со
смещениями, строки), SEE DUP (asm word), SEE RAMKA (92 строки с DO LOOP,
без рассинхрона). Регрессии: test.f, запуск без файлов (старый D-цикл),
базовый набор repl.f (арифметика, многострочное ":", DO LOOP).

## heap.f и strings.f - память и строки ДО консоли (сделано)

Порядок загрузки: `console_forth.exe heap.f strings.f console.f wincon.f repl.f`
heap.f нужен только auto-загружаемый stdlib.f; strings.f - только heap.f +
ядро. Ранний минимум без консоли: `console_forth.exe heap.f strings.f`
(старый D-цикл REPL, строки уже работают - $. печатает через kernel TYPE).

### heap.f - память + учёт выделений

- msvcrt открыта под СВОИМ именем `crtm` со своим LibraryLoad (LibraryLoad
  должен идти после всех регистраций функций этой DLL; двойной LoadLibrary
  безопасен - refcount). console.f оставила свой `crt` для putchar/getch/...
- Слова: MALLOC CALLOC REALLOC FREE MSIZE MEMSET MEMMOVE (перенесены из
  console.f) + HALLOC HSIZE HFREE HFREEALL HCOUNT HBYTES.
- Формат блока HALLOC (заголовок встроен, одна аллокация вместо двух):

### DEPTH ( --> n ) - asm-примитив, forth.d:769 h_DEPTH, регистрация :2024

Формула: глубина = (gResetEBP - EBP) / 4. Код:
`mov ECX,EBP; call h_DUP; mov EAX,gResetEBP; sub EAX,ECX; sar EAX,2; ret`.

снятого ДО h_DUP. Пустой стек -> 0. Проверено: `1 2 3 DEPTH .` -> 3.

## LEAVE (сделано) - досрочный выход из цикла

asm-примитив `(LEAVE)` (forth.d, после f_s_DO_s; регистрация рядом с
(LOOP)/(+LOOP)): `lea ESI,[ESI+CELL*2]; ret` - снимает пару
индекс/предел с L-стека. Прыжок за тело цикла делает скомпилированный
следом BRANCH. Баланс L-стека: обе ветки выхода (естественная через
(LOOP) и досрочная через (LEAVE)) снимают ровно одну пару.

Цепочка резолвов (бутстрап, перед DO/LOOP):
- `VAR LVCHAIN` - голова цепочки неразрешённых LEAVE текущего цикла.
  Звено = ячейка смещения BRANCH; внутри звена лежит адрес предыдущего
  звена (0 = конец), при резолве перезаписывается смещением.
- `LVRES` - пройти цепочку, резолвя каждое звено через RESOLVE>
  (смещение относительно адреса ячейки - так устроен рантайм BRANCH:
  `pop EBX; add EBX,[EBX]; jmp EBX`).
- `LEAVE`: `?COMP COMPILE (LEAVE) COMPILE BRANCH CELL ALLOT >MARK DUP
  LVCHAIN @ SWAP ! LVCHAIN ! ; IMMEDIATE` - ячейка смещения одновременно
  является звеном цепочки.
- DO кладёт ЧУЖУЮ цепочку на стек компиляции под меткой цикла
  (`LVCHAIN @ 0 LVCHAIN !` до `<MARK`), LOOP/+LOOP после `<RESOLVE`
  делают `LVRES LVCHAIN !` - вложенные циклы не пересекаются.
  ВНИМАНИЕ: стек компиляции при DO держит ДВА элемента (чужая цепь,
  метка), не один - не смешивать с BEGIN/WHILE внутри одной конструкции.
- LEAVE вне DO..LOOP - UB: примкнёт к чужой цепи и прыгнет в чужой LOOP.

Проверено: обычный выход по условию; вложенный (внутренний LEAVE не
трогает внешний цикл, J корректен); два LEAVE в одном цикле;
безусловный LEAVE (1 итерация, код после LOOP выполняется);
LEAVE + +LOOP; DEPTH=0 после всех тестов; регрессии strings/heap/test.f.

## CATCH/THROW (сделано) - настоящая размотка, Ошибка 1 закрыта

### Слова

- `CATCH ( xt -- exc# | 0 )` - asm-примитив h_CATCH (forth.d, после
  f_EXECUTE; регистрация рядом с THROW). Исполнить xt, перехватить THROW.
  Успех: 0 поверх результатов xt. THROW: exc# на вершине, стеки в состоянии
  на момент CATCH.
- `THROW ( n -- )` - переделанный f_THROW. n=0 - no-op (ANS). n!=0:
  есть активный CATCH - размотка до него; нет - печать "[n] THROW - error"
  + abort строки до границы evalForth/executeForth (тёплый сброс, как раньше).

### Механика

Фрейм CATCH - 3 ячейки на стеке возвратов (ESP):
`[savedEBP][savedESI][old HANDLER]`, глобал gCatchHandler = ESP фрейма
(цепочка вложенных CATCH). Между CATCH и THROW все кадры - чисто фортовские
(native call/ret), поэтому размотка ESP безопасна: D-кадры лежат ниже
чекпойнта границы и не трогаются.

- Нормальный возврат xt: epilogue в h_CATCH (снять фрейм, HANDLER := old,
  положить 0, ret к вызывавшему).
- THROW к CATCH: f_THROW сам исполняет тот же epilogue (savedEBP -> EBP,
  savedESI -> ESI, HANDLER := old, ESP := фрейм+12 - там ret-адрес вызова
  слова CATCH) и делает ret прямо к вызывавшему CATCH с exc# в EAX.
  Адрес resume хранить НЕ нужно - [ESP] после снятия фрейма = ret-адрес.

### THROW без CATCH - чекпойнт границы D<->Форт

evalForth и executeForth перед исполнением сохраняют gEvalESP (позиция
сохранённых D-регистров на стеке) и gEvalResume (адрес продолжения,
захватывается трамплином `call cap; jmp res; cap: pop EBX; mov gEvalResume,
EBX`). f_THROW без CATCH: печать через h_THROW + `mov ESP,gEvalESP;
jmp gEvalResume` - эпилог границы отрабатывает штатно. Каждый вход
обнуляет gCatchHandler (фреймы не живут между строками/вызовами).
executeForth при THROW возвращает хосту КОД ошибки (не результат).

### Неизвестное слово

f_inter на не-слове-не-числе бросает THROW -13 (ANS "Undefined word";
"Not find word [X]" по-прежнему печатается в number()). Раньше строка
молча продолжалась - отсюда были краши REPL (`A B S=` на мусоре).

### Проверено

CATCH ловит (exc# на вершине, баланс стека DEPTH=0); результаты xt под 0;
0 THROW - no-op; THROW через вложенные DO-циклы (L-стек восстановлен);
вложенные CATCH (внутренний ловит, внешний - нет; re-throw через ELSE
THROW работает, классический шаблон: `CATCH IF ... ELSE ... THEN`);
неизвестное слово обрывает строку без краха; ?COMP обрывает строку;
регрессии: strings/heap/LEAVE/SEE/test.f/ранний режим.

### Изменение поведения (осознанное)

Строка с ошибкой ОБРЫВАЕТСЯ, а не продолжается до конца. Все места,
полагавшиеся на «THROW напечатает и пойдём дальше», надо пересматривать
под CATCH (шаблон: `' XT CATCH IF обработка THEN`).

### Слова поверх CATCH/THROW (бутстрап forth.d, после ?COMP/?EXEC)

- `ABORT ( -- )` = `-1 THROW ;`
- `?PAIRS ( n1 n2 -- )` - равны -> снять оба, иначе THROW -22 (ANS
  "control structure mismatch"). Строительный блок для compile-only
  проверок парности (значения-маркеры кладут слова управления).
- `?PAIRS" ( n1 n2 "ccc" -- )` - то же + печать текста при несовпадении;
  IMMEDIATE, исполняется во время компиляции (проверки внутри
  определяющих слов).
- `ON-ERROR ( xt -- exc# | 0 )` = синоним CATCH (SPF-совместимость для
  чтения чужих исходников).
- `EXIT-ERROR ( exc# -- )` - exc# != 0 -> перевыброс THROW, иначе снять.
  Шаблон: `['] XT CATCH EXIT-ERROR` - "пробросить ошибку наверх, если была".

Проверено: ABORT обрывает строку; ?PAIRS оба пути; ON-ERROR ловит/пускает;
EXIT-ERROR перевыбрасывает (внешний CATCH видит код) и пропускает успех.
ВНИМАНИЕ: результаты xt остаются под exc# (ANS) - после `' OK CATCH .`
на стеке остаётся 42.

## Структуры + UNLOOP/?DO (сделано, forth.d)

### Структуры (бутстрап, после CR)

`: STRUCT 0 ; : FIELD CREATE OVER COMPILE (CREATE) , + DOES> @ + ; : /STRUCT CONST ;`

Идиома: `STRUCT CELL FIELD MODE CELL FIELD SPEED /STRUCT /CFG`. Имя даёт
ТОЛЬКО /STRUCT (STRUCT лишь кладёт 0). Поле: ( base -- base+off ).
Три системные особенности, БЕЗ которых не работает (обнаружены отладкой):
1. CREATE в этой системе НЕ оставляет body-addr на стеке - h_CREATE
   заканчивается setToAdr со ПУСТЫМ стеком. Поэтому классический вид
   `CREATE OVER , +` здесь означает: `,` пишет смещение прямо в body
   (HERE=body), без всякого адреса со стека.
2. В body ОБЯЗАТЕЛЕН `COMPILE (CREATE)` до `,` (как у CONST/VAR) - он даёт
   рантайм, кладущий body-addr на стек данных перед DOES-хвостом. Без него
   CFA слова-поля указывает в мусор -> Breakpoint/AV.
3. Голый CREATE (без CONST/VAR/DOES) даёт слово, которое НЕЛЬЗЯ исполнять -
   его CFA-рантайм портит адрес возврата (AV после печати). Экземпляры:
   `HERE /CFG ALLOT CONST cfg` (паттерн test.f) или `/CFG HALLOC CONST cfg`.
Грабли отладки: R@ читает ВТОРУЮ ячейку стека возвратов ([ESP+CELL]) -
   caller-адрес, а НЕ то, что только что сделал >R; классический FOR-стиль
   CREATE OVER , + пытался чинить то, что не было сломано - ломка пришла
   из теста (лишнее имя после STRUCT).

### UNLOOP + ?DO

- `UNLOOP ( -- )` = `(LEAVE)` - снять пару индекс/предел с L-стека перед
  EXIT из тела цикла.
- `?DO` - цикл с нулём итераций. Рантайм `(?DO)` (asm, рядом с (DO)):
  равенство предел=индекс -> снять пару, флаг FALSE (прыжок за цикл);
  иначе положить пару как (DO), флаг TRUE (войти). Прыжок-пропуск связан
  в цепочку LVCHAIN как звено LEAVE и резолвится LOOP/+LOOP тем же LVRES -
  LOOP не изменялся, отдельный ?LOOP не нужен.
- КЛЮЧЕВОЙ подводный камень (?DO): ?BRANCH ВСЕГДА потребляет флаг (обе
  ветки) - под флаг нужно вернуть прежний TOS в память (паттерн (LOOP)
  на ветке выхода: `lea EBP,[EBP-CELL]; mov [EBP],oldTOS`). Без этого
  нуль-итерационный пропуск уводил глубину стека в -1. Установлено
  микротестом `: H 5 3 < IF 111 ELSE 222 THEN ; H DEPTH .` -> 1
  (только 222 - флаг снят).

## +! 1+! 1-! (сделано, ядро forth.d)

asm-примитивы после h_setToAdr (образец `!`), регистрация рядом с `!`:
- `+! ( n a-addr -- )` - h_addToAdr: [a-addr] += n
- `1+! ( a-addr -- )` - h_incToAdr: [a-addr]++
- `1-! ( a-addr -- )` - h_decToAdr: [a-addr]--
Каждое 5 строк asm. Закрывают вечную граблю `VAR @ 1+ VAR !`.
Грабли регистрации: в D-строке счётчик длины - ЭТО БАЙТ; для длины >= 8
нужен 3-значный октал `\003` (`\31` = байт 0o31=25, слово не находится).
1+! берёт ТОЛЬКО адрес - `1 x 1+!` протекает литералом 1 на каждой
итерации (тест ловил DEPTH=10 вместо 0).

Упрощение рабочего кодa на +!/1+!/1-! (console.f): HOLD, EDELETE, EBACKSP,
EINSERT, стрелки <- ->. Все места вида `VAR @ 1+ VAR !` заменены.
strings.f НЕ тронут: там `@ 1+` - арифметика указателей (значение+1), а не
инкремент ячейки. test.f не тронут (легаси-фикстура).
Грабли тестирования: `#> TYPE` КРАШИТ (системный TYPE = asciiz, а #>
выдаёт пару addr len) - `.`/`U.` печатают через TYPEC. Правильно:
`<# #S #> TYPEC`. Это не баг HOLD - краш воспроизводился и со старым.

### FAKEWIN - симуляция колбэка из чистого Форта (рабочая)

```
: FRET ;
: FAKEWIN ( -- )
    SP@ 64 - GSAVE ! LP@ 64 - GSAVE 1+!
    0 >R 0 >R 0 >R 0 >R          \ lp wp msg hwnd (реальные значения!)
    ['] FRET >R                  \ фальшивый ret-адрес (colon-слово = ret)
    [ 194 B, 16 B, 0 B, ] ;      \ ИНЛАЙН ret 16 - НЕ словом!
FAKEWIN CR ." ok" CR
```
ГРАБЛИ СИМУЛЯЦИИ (ложные следы на 2+ часа): (а) ret 16 СЛОВОМ ([ 194 B, ]
; ) вместо инлайн-байтов - call слова кладёт лишний ret-адрес на вершину,
механика ломается В ТЕСТЕ, а не в мосту; эмпирика "противоречила модели",
пока виноват не оказался тест. (б) порядок: фальшивый ret-адрес кладётся
ПОСЛЕ аргументов (>R), он оказывается на вершине - как у реального stdcall.
(в) в симуляции не воспроизводится нерешённая проблема - реальный контекст
имеет живые user32-фреймы.

## Поведение CDECL-Call" / WINAPI-Call" — проверено тестами (файл t21-t25)

### Контракт (подтверждён тестами)

Оба слова: `Library@ handle N CDECL-Call|WINAPI-Call" Имя" ИМЯ` создают слово,
которое снимает РОВНО N значений со стека данных (N = зарегистрированное
число, НЕ фактическое число положенных!) и кладёт результат. Контракт callD:
результат в EAX, +1 мусорная ячейка под ним (слово само делает DROP).

| Проверка | Результат |
|---|---|
| cdecl abs(-7) | 7 |
| winapi GetSystemMetrics(0) | 2560 (реальная ширина экрана) |
| winapi GetDesktopWindow()/GetTickCount() | ненулевые |
| cdecl strchr("abc",'b') | 'b' (cdecl с 2 аргументами) |
| winapi IsWindow(0) | 0 |
| Баланс СТЕКА ДАННЫХ (DEPTH до/после, верное N) | сбалансирован (-1=TRUE) |
| Баланс МАШИННОГО стека: 300001 итерация в цикле | ОБА выжили (stdcall callee чистит сам; cdecl чистит RDROP слова) |
| Вызов изнутри : определения + код после | норма (DEPTH чист) |
| Лишний АРГУМЕНТ НА ДАННЫХ (2 положили, N=1) | +1 ячейка на данных, машинный стек ЧИСТ (слово двигает только N!) |

### Ключевые выводы

1. Слово переносит на машинный стек РОВНО N зарегистрированных аргументов.
   Лишние данные остаются на стеке данных (растёт глубина) - безвредно,
   но DEPTH портится. Недостача = недостача на данных (underflow).
2. Машинный стек сбалансирован ПРИ ЛЮБОМ числе данных-аргументов - утечек
   от "передал лишнее" НЕТ. Это опровергает гипотезу сессии (смерть WTEST
   НЕ связана с числом аргументов).
3. N ограничено 4 (ветка ELSE _-Call" молча всё выбрасывает) - для
   большего использовать GADR-Call" + ручной >R×N + CALL_A (см. CWIN12).
4. Регистрация WINAPI-функции как CDECL (или наоборот): вызовы ПРОХОДЯТ
   (даже 10 подряд, даже цикл 100000), но каждый вызов съедает 4 байта
   чужого фрейма (двойная чистка аргумента: callee ret N + RDROP слова).
   Латентная порча - рано или поздно ломается чужой return. ИЗБЕГАТЬ.
5. Настоящие машинно-стековые катастрофы доказаны только две:
   (а) ручной RDROP после stdcall-вызова (баг CWIN12: 48 байт чужого
   фрейма -> "молчаливый exit 0" - процесс доходит до main без дампа);
   (б) зеркальная: отсутствие RDROP после cdecl -> утечка вниз.
   Признак (а): процесс исчезает, exit code 0, без дампа (НЕ путать
   с зависанием = timeout 124).

### Грабли тестирования

- S" в ИНТЕРПРЕТАЦИИ кладёт ДВЕ копии адреса (WORD DUP): `S" abc" 1+ ...`

## _-Call" расширен до ЛЮБОГО числа параметров (stdlib.f, сделано)

Ветки 0-4 обоих соглашений (cdecl/winapi) НЕ ТРОНУТЫ (байт-в-байт как в arx/).
Бывшие заглушки `ELSE DROP L> DROP` (>4 параметров молча всё выбрасывали)
заменены универсальными ветками с циклом:

    DUP _CCN ! DROP           // n -> VAR _CCN (определён ДО _-Call"!), count прочь
    _CCN @ 0 DO >R LOOP       // все n аргументов -> машинный стек
    L> CALL_A DROP            // вызов; cdecl-ветка дальше: + _CCN @ 0 DO RDROP LOOP

[ESP+CELL] = чужой адрес возврата, НЕ то, что положил >R!). Реентерабельность
_CCN: система однозадачная, вложенных _-Call" в аргументах не бывает.

## Эксперимент "живые регистры" (ОТВЕРГНУТ, forth.d возвращён к GSAVE-варианту)

Гипотеза: раз наш цикл сообщений - чистый Форт, а stdcall сохраняет
EBX/ESI/EDI/EBP, то в момент колбэка "наши" регистры живы и GSAVE не нужен
(как в автономных Фортах типа SPF). Реализовано (forth.d, wndProcBridge без
подмены EBP/ESI), протестировано, ОТКАЧЕНО.

Почему отвергнута - ключевое понимание ABI: когда user32 вызывает WndProc,
регистры EBP/ESI/EBX/EDI содержат ЗНАЧЕНИЯ USER32 (его фрейм и рабочие
регистры). Сохранение callee-saved работает ТОЛЬКО между нашим кодом и
непосредственным вызовом DispatchMessage: user32 прячет наши значения в
СВОИХ кадрах и вернёт их ПОСЛЕ возврата DispatchMessage. В ГЛУБИНЕ колбэка
"наших" регистров в CPU НЕТ и быть не может - телепортации регистров в
колбэк не существует. Обработчик с живыми регистрами писал по фрейму
user32 -> повреждение -> смерть в том же месте (маркер K есть, J нет).
Вывод: GSAVE/MSGSAVE - АРХИТЕКТУРНО НЕОБХОДИМЫ, не костыль. (Как восстанавливает
контекст SPF - отдельный вопрос, вероятно тоже через свой SAVE-механизм.)

НОВЫЙ ФАКТ по открытой проблеме: смерть НЕ зависит от источника регистров
(GSAVE-контекст и user32-контекст умирают в ОДНОМ месте - внутри вызова
DLL-функции из обработчика). Значит виновник - не регистровый контекст,
а что-то в самом акте "Форт -> CALL_A -> DLL" внутри реального колбэка.
Следующие кандидаты для проверки: (1) D-обёртка над вызовом (разделит
"callD в колбэке" vs "контекст колбэка"); (2) машинный стек: глубина/
значения фреймов user32 ниже ESP, с которыми пересекается _-Call"
(проверить: зонд - прочитать [EBP-...] цепочку фреймов в момент колбэка).

## КОЛБЭК-ПРОБЛЕМА РЕШЕНА (окно Windows работает, WTEST OK)

### Диагностический путь (что разделило проблему)

Эксперимент с D-обёрткой (d_CallStockObject, ячейка 16): обработчик звал
обёртку через CALL_A - УМЕР. Но EMIT внутри обработчика РАБОТАЕТ, а EMIT
зовёт d_emit НАПРЯМУЮ (call d_emit), минуя callD. Общее у погибших путей:
CALL_A -> callD. У живого: прямой call. ВИНОВНИК - полный callD
(pop/SL_toL/h_DUP/SL_Lfrom/push) внутри реального Windows-колбэка.
Микропричина шага осталась неустановленной (кандидаты: SL_toL/SL_Lfrom
на L-стеке в контексте GSAVE), но не нужна - есть обход.

### Решение (два элемента)

1. callD2 ("CALLB", forth.d): упрощённый шлюз - mov ECX,EAX; call ECX;
   call h_DUP; ret. Тот же контракт, что у CALL_A (результат + DROP).
   В реальном колбэке РАБОТАЕТ (доказано: обработчик через CALLB дожил
   до J-маркера и дальше). Прямой вызов DLL из обработчика теперь писать:
   stdcall:  args >R×N XFN CALLB DROP ; cdecl: + RDROP×N после CALLB.
2. Архитектурный паттерн "флаг в обработчике - реакция в цикле":
   обработчик = ЧИСТЫЙ ФОРТ (MQ-поля, сравнение, флаг), всем сообщениям
   возвращает 1 (WM_NCCREATE требует TRUE иначе создание прерывается),
   WM_DESTROY -> флаг WQUIT + 0. Цикл PUMP ПЕРЕД GetMessageA проверяет
   флаг и сам постит PostQuitMessage - там DLL-вызовы законны.
   Рамку/заголовок/кнопку закрытия рисует и обрабатывает сама система,
   окно полнофункционально (двигается, закрывается по крестику).

### WTEST (автотест, проходит целиком, RC=0)

WINOPEN (окно создаётся, мост обрабатывает синхронные сообщения создания)
-> SendMessage(WM_DESTROY) синхронно через мост -> флаг -> PostQuitMessage
-> PUMP (GetMessageA: 1 - отложенное сообщение создания, 0 - WM_QUIT)
-> DestroyWindow -> "WTEST OK".

### Грабли финала (коротко)

- Обработчик, возвращающий 0 на ВСЕ сообщения: WM_NCCREATE=0 -> создание
  окна прерывается ("CreateWindowEx failed"). Всем -> 1, WM_DESTROY -> 0.
- Зависание WTEST: флаг ставился ДО входа в PUMP, а проверка была только
  ПОСЛЕ Диспатч -> первый GetMessageA блокировался навсегда. Проверку
  флага перенесли в начало тела BEGIN...UNTIL.
- В тесте t29 (12-параметровый CreateWindowExA) окно создавалось и
  уничтожалось через DefWindowProcA как WndProc (GADR-Call") - классика
  работает независимо от моста.

### Состояние файлов (финал)

- forth.d: мост GSAVE-вариант (h_CATCH, выравнивание, глобалы-аргументы),
  callD2/CALLB, d_CallStockObject (ячейка 16) - оставлен как дискриминатор
  и путь для прямых вызовов из обработчика.
- win.f: чистый финал (без маркеров): WPH (флаг), PUMP (проверка флага
  перед GetMessageA), WTEST с явным PostQuitMessage, WIN для живого запуска.
- stdlib.f: _-Call" с универсальными ветками (>4 параметров), VAR _CCN.

## CALLB (callD2) ВЕРИФИЦИРОВАН в обычных контекстах (универсален)

Итог шага 1: CALLB работает И в колбэке, И в обычном коде. Мост D<->Форт
теперь ДУБЛИРОВАН: CALL_A (callD) - весь обычный код (stdlib на нём, не
трогаем), CALLB (callD2) - везде, включая Windows-колбэки.

Проверено (t32/t33/t34): cdecl-1 abs(-7)=7; winapi-1 GSM(0)=2560;
winapi-0 GetTickCount/GetDesktopWindow; cdecl-5 _snprintf "<42>"+4;
winapi-7 SetWindowPos->0; цикл 300001 итерация ОБОИХ соглашений без
переполнения; регрессия WTEST OK.

### Две ошибки в реализации callD2, найденные верификацией (ВАЖНО)

1. callD2 ОБЯЗАН сделать pop/сохранить/push своего ret-адреса вокруг
   call ECX - иначе аргументы остаются НИЖЕ ret, и callee видит ret-адрес
   КАК ПЕРВЫЙ АРГУМЕНТ (всё сдвинуто на ячейку; abs вернул |ret-адрес|).
   ЭТО ЖЕ объясняет загадочную поломку загрузки месячной давности от
   "упрощения" callD - упрощение было неэквивалентным именно здесь.
   Полный callD делает то же самое (pop EAX), просто прячет ret на
   L-стеке вместо регистра.
2. Прячать ret нужно в EBX (callee-saved) - в EDX callee его портит
   (caller-saved), и ret уходит в мусор -> AV.

Итоговый callD2: mov ECX,EAX; pop EBX; call ECX; push EBX; call h_DUP; ret.
Контракт как у CALL_A: результат в EAX + 1 мусорная ячейка (вызывающий
DROP). Формы: stdcall - args >R*N fn CALLB DROP; cdecl - + RDROP*N.

### Грабли ТЕСТОВ (не системы) - чтобы не повторять

- GetTickCount в KERNEL32, не user32 ("Error find function" -> 0 -> call 0).
- 0-параметровой stdcall-функции НЕ нужен фиктивный аргумент >R (ret 0
  его не съест, останется на машинном стеке -> порча чужого фрейма).
- CALLB DROP оставляет РЕЗУЛЬТАТ на стеке (DROP снимает только мусор) -
  в цикле нужен второй DROP, иначе на 300001-й итерации переполнение.

1. LoadCursorA регистрировался с N=1 вместо 2 -> курсор 0, класс с пустым

2. WPH делал RDROP x5 после stdcall-вызова через CALLB -> съедал 20 байт

ГЛАВНЫЙ БАГ ЦИКЛА СООБЩЕНИЙ (симптом: молчаливая смерть RC=127 за ~111 мс
после показа окна; WTEST проходил):

- Архитектурный паттерн "флаг в обработчике - реакция в цикле" распространён
  и на paint: WPH чистая логика, вся работа с API - в PUMP.

УРОКИ ПО ДОРОГЕ (все внесены в win.f/console_forth.d):
- Мост wndProcBridge + выравнивание (and ESP,-16; sub ESP,12 + gap) - РАБОЧИЙ
  для чисто-фортовых обработчиков, оставлен как стенд; выравнивание

- CALL_A в void-контексте требует DROP DROP (результат под мусором) -

- S" в интерпретации кладёт адрес дважды: идиома `S" x" 1+ CONST N DROP`.
- СБОРКА: dmd -m32 forth.d console_forth.d -ofconsole_forth.exe
  "-L/C:/D/dmd2/windows/lib32mscoff/mingw/user32.lib" (хост теперь линкует

## КОРРЕКЦИЯ по балансу стека (важно!)

После восстановления ПОЛЬЗОВАТЕЛЕМ stdlib.f: слова `_-Call"` (обе ветки)
заканчиваются `CALL_A DROP` - дубль результата снимается ВНУТРИ слова,
слово оставляет РОВНО ОДИН результат. Следствия:
- Вызов "ради эффекта" (void): ОДИН DROP после слова. `DROP DROP` даёт
  underflow - 2 ячейки на каждое сообщение цикла (симптом: DEPTH уходит
  в минус, "стек плывёт", -628 за ~314 сообщений). Ранее в win.f
  рекомендовался DROP DROP - это ошибка ДЛЯ ЭТОЙ ВЕРСИИ stdlib, откачена.
- Контракт callD (forth.d:1624): h_DUP ПОСЛЕ call - результат дважды
  (EAX + ячейка), ветка _-Call" снимает одну копию DROP-ом.
- Другие места согласованы: `0 PostQuitMessage DROP` (DROP был ДОБАВЛЕН,
  раньше результат оставался), GetStockObject - 1 параметр (звали с
  двумя нулями - лишний 0 на стеке), WINOPEN оставляет +1 (косметика,
  не дрейфует).
- Проверено: WINOPEN/WTEST/WIN сбалансированы, живой цикл стабилен.
